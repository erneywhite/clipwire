# Архитектура Clipwire

Документ начинался как проект к этапу 2 и с тех пор дополнялся по мере работы. Разделы с
пометкой «этап 2» описывают исходные решения; где они изменились, это сказано рядом.
Состояние на 0.10.0 и доступ ИИ-инструментов по MCP (ноябрь 2026).

## Компоненты

Один Cargo-workspace:

| Крейт | Что это | Где работает |
|---|---|---|
| `clipwire-core` | Модель элемента буфера, шифрование, формат сообщений, защита от петель | библиотека |
| `clipwire-agent` | Движок синхронизации: следит за буфером, отправляет и получает элементы, локальная история, политика доступа ИИ | Windows, macOS, Linux |
| `clipwire-server` | Почтовый ящик (офлайн-доставка, история с TTL) и встроенный iroh-relay | Docker |
| `clipwire-desktop` (`apps/desktop`) | Приложение на Tauri 2 и Svelte 5: трей, окно вставки, настройки, автообновление, канал для ИИ-инструментов | Windows, macOS, Linux |
| `clipwire-desktop --mcp` | Мост MCP для ИИ-клиента: stdio-сервер MCP, ходит в запущенное приложение по локальному каналу | там же, его запускает ИИ-клиент |

Сервер собран в один бинарник и один контейнер. Relay встроен через
`iroh_relay::server` (фича `server`), отдельного контейнера для него нет. Тому, кто
захочет поднять свой сервер, хватит одного `docker compose up` и записи в nginx.

## Сеть

Все соединения идут через iroh: QUIC с TLS, у каждого устройства своя пара ключей
Ed25519 (endpoint ID). Если UDP пройти не может, iroh сам уходит через relay по
HTTPS/WebSocket, поэтому снаружи достаточно 443 за обратным прокси. Если откроем ещё и
UDP-порт, соединения с сервером пойдут по QUIC напрямую и станут быстрее.

**Этап 2 — схема «звезда»:** агент держит одно соединение с сервером (ALPN
`clipwire/2`). Сервер раздаёт элемент остальным устройствам группы, которые сейчас в
сети, и хранит последние N элементов с TTL для тех, кто офлайн.

Протокол (`crates/clipwire-core/src/proto.rs`): агент шлёт `JoinWithToken` (секрет
группы и токен сервера из приглашения, тот же, что у relay), сервер отвечает
`Joined`, затем историю группы по элементу (`History`) и `HistoryEnd`. Старый сервер
`JoinWithToken` не знает и рвёт соединение, не ответив; если на вход с токеном
сервер закрыл соединение или ответил `Error`, агент один раз повторяет вход обычным
`Join` по новому соединению. Отказ второго входа показывается с причиной первого,
если сервер её назвал. История идёт
отдельными кадрами, потому что картинки вместе не влезают в один кадр. Дальше агент шлёт
`Push` (новое копирование), сервер раздаёт его как `Deliver`.

Сейчас основной ALPN — `clipwire/3`. Агент предлагает серверу ещё `clipwire/4`: формат
тот же, но по нему можно спрашивать `GetStats` (сколько элементов и файлов группы лежит
на сервере). Сервер 0.1.2 и новее выбирает `/4`, старый — `/3`, и агент по выбранному
ALPN понимает, какие сообщения слать: незнакомое сообщение старый сервер встречает
обрывом соединения. Новые сообщения дальше добавляются так же, следующим номером ALPN.

`clipwire/5` добавляет удаление на всех устройствах: `Delete` от агента и `Deleted` от
сервера. id одной записи на разных устройствах разные (при отправке элемент получает
новый id, одинаковое содержимое история склеивает по хэшу), поэтому удаляется по
`Content::hash`. Хэш короткого текста подбирается перебором, поэтому записка
(`DeleteNote`: хэши и время удаления) шифруется ключом группы (`crates/clipwire-core/src/delete.rs`).
Сервер хранит записки столько же, сколько историю (не больше 200 на группу), рассылает
их соединениям по `/5` и отдаёт все хранящиеся сразу после `HistoryEnd`. Получатель не
трогает закреплённое и записи, появившиеся позже времени удаления (с запасом 5 секунд на
расхождение часов). Отправлять удаление или нет, решает настройка «Удалять на всех
устройствах», по умолчанию выключенная. Удаления без связи копятся в памяти движка и
уходят после входа.

`clipwire/6` добавляет `DevicesChanged` от сервера: устройство группы подключилось,
отключилось или опубликовало карточку (новое имя). Сервер рассылает его остальным
соединениям по `/6`, а открытый список устройств в настройках перечитывает `ListDevices`.
Фонового опроса нет: закрытая вкладка ничего не запрашивает.

`clipwire/7` добавляет `ServerInfo`: после входа сервер сообщает свою версию. Клиент
показывает её в «Состоянии» и один раз уведомляет, если протокол сервера младше
протокола клиента (`proto::server_outdated`); версии программы не сравниваются, поэтому
выпуск без изменений сервера обновить образ не просит. Сервер до
`/7` версию не сообщает, клиент считает его старым. Возможности проверяются по номеру
протокола (`alpn_version`), а не перечислением ALPN, чтобы новая версия не теряла старые.
Клиент не синхронизируется с сервером ниже `MIN_SERVER_PROTOCOL` (сейчас `/8`: без закрепов
группы клиент работать не будет; поднимается, когда новой возможности старый сервер не заменить).
Со старым сервером клиент рвёт соединение с понятной ошибкой и событием `ServerOutdated`.

`clipwire/9` добавляет администрирование сервера из клиента и роли в группе
(`crates/clipwire-core/src/admin.rs`, `crates/clipwire-server/src/admin.rs`). Без запроса
сервер по `/9` новых сообщений не шлёт, поэтому клиенту, который их не знает, `/9` безопасен.
Устроено так:

- **Два секрета сервера.** Токен relay пускает к relay и остаётся в коде приглашения. Ключ
  администратора (32 случайных байта, `<data_dir>/admin.key`, права 0600) сервер создаёт при
  первом запуске, если файла нет. Он есть только в коде сервера `cwserver2-…`
  (`AdminServerInfo`: прежний `ServerInfo` и ключ), в код приглашения не попадает. Старый код
  `cwserver1-…` по-прежнему разбирается (`ServerCode::decode`), но группу с ним не создать.
- **Создание группы** — только `JoinAsAdmin { group_id, join_secret, admin_key }`; создатель
  становится админом группы (таблица `group_admins`, см. `clipwire/13` ниже). Неверный ключ — ответ
  `AdminFailed(BadKey)` вместо `Joined`: агент по нему понимает, что ключ устарел, забывает
  его (событие `AdminKeyStale`, приложение удаляет `admin.bin` и просит новый код) и входит
  снова с `JoinWithToken`. На голый `Join` он при этом не падает: после смены токена relay
  сервер его не принимает. `JoinWithToken` с верным токеном
  relay создаёт группу в одном случае: это новая группа для смены ключа, а устройство может
  сменить ключ хоть одной своей живой группы (оно её админ или у группы админа нет). Такая
  группа помечена `pending_by` («незавершённая»), у устройства она одна (следующая удаляет
  прошлую со всем содержимым), и без `Rekey` через час удаляется, что бы в ней ни лежало. В
  незавершённой группе можно только то, что нужно для смены ключа: карточку, настройки и
  закрепы группы (агент перешифровывает их новым ключом до `Rekey`) и запросы списков.
  `Push`, `Backfill` и `Delete` получают `Error`, загрузка файлов — `BlobFail::Protocol`:
  иначе такая группа была бы хранилищем в обход предела групп. Агент входит в новую группу
  всегда с токеном, без ключа администратора, даже если он есть. В существующую группу
  пускают все три входа, как раньше: старые клиенты `/3`–`/8` входят с токеном и дальше.
- **Админ группы.** Только админ шлёт `Rekey`, то есть меняет ключ и удаляет устройства (удаление
  — это смена ключа без пакета для удаляемого). Новой группой в `Rekey` сервер принимает
  только незавершённую группу, которую создал сам отправитель (`pending_by` = он) и где он
  один: иначе админ своей группы перевёл бы её устройства в существующую чужую группу и
  стал бы там админом. Админы новой группы наследуются от старой (с `/13` их может быть
  несколько, правило ниже), уже заданные не перезаписываются. Одно устройство меняет ключ не чаще 10 раз за сутки
  (`MAX_REKEYS_PER_DAY`, по `groups.rotated_by`). Роль передаётся
  `TransferGroupAdmin { device }` устройству этой группы, остальным уходит `DevicesChanged`.
  Кто админ, говорит `GetGroupAdmin` → `GroupAdmin { admin }` (в `DeviceEntry` поля нет:
  старые клиенты не разобрали бы список). У групп, созданных до 0.5.0, админа нет: ключ там
  по-прежнему меняет любой участник, а админом становится первое устройство, вошедшее с
  ключом администратора (`JoinAsAdmin` или `AdminAuth` в группе). Если админ потерян
  (устройство сломано или пропало), администратор сервера из этой группы забирает роль
  явным `ClaimGroupAdmin` → `GroupAdmin { admin }` и при живом админе; без прав
  администратора — `AdminFailed(NotAuthorized)`. В приложении это кнопка «Стать админом
  группы» с подтверждением в списке устройств.
- **Администратор сервера.** `AdminAuth { key }` (сравнение за постоянное время) → `AdminOk`
  или `AdminFailed(BadKey)`; можно первым сообщением, тогда соединение без группы и только
  для администрирования. После него: `GetServerSettings` / `SetServerSettings` →
  `ServerSettings { values, defaults, stored }`, `GetServerSummary` → `ServerSummary`,
  `RotateRelayToken` → `RelayTokenRotated { server_code }`, `RotateAdminKey` →
  `AdminKeyRotated { server_code }`. Код в этих ответах — `SecretCode`: в кадре обычная
  строка, в отладочном выводе `SecretCode(..)`, а в лог сервера новый код не пишется (его
  получает клиент; при запуске сервер печатает код в лог, см. README). Отказы —
  `AdminFailed(AdminFail)`, соединение остаётся. Соединение помнит номер ключа, с которым
  вошло: после смены ключа его права пропадают; агент, получив `NotAuthorized`, проверяет
  свой ключ повторным `AdminAuth` и забывает его, если тот не подошёл. Команды
  администратора в приложении принимаются только из окна настроек.
- **Настройки сервера** лежат в таблице `settings(key, value)`. Действующее значение — из
  базы, иначе из переменной окружения, иначе встроенное; сброс удаляет строку. Пределы
  читаются из общего состояния (`Shared::limits`) на каждый запрос, поэтому новые значения
  действуют сразу. Допустимые пределы каждой настройки — в `clipwire_core::admin::SETTINGS`,
  при отказе не меняется ни одна из присланных.
- **Смена токена relay** пишет новый `relay.token`, relay сразу проверяет новый токен
  (собственный эндпоинт сервера пускается всегда), все соединения Clipwire закрываются с
  `Error`. Обычный `Join` после этого не принимается: агент повторяет вход без токена, если
  вход с токеном отклонён, и иначе старый код приглашения продолжал бы работать. Токен из
  `CLIPWIRE_RELAY_TOKEN` из клиента не меняется (`AdminFailed(Unavailable)`). Остальные
  устройства вводят новый код приглашения прямо в «Синхронизации» («Новый код приглашения»,
  поле открывается само при отказе по токену): если ключ группы в коде тот же, меняется
  только `invite.server` в `state.bin`, ключ устройства и группа остаются
  (`clipwire_agent::admin::adopt_invite`, в консоли `reinvite`). Приглашение в другую группу
  или на другой сервер так не принимается. Новый код сервера администратора с другим
  токеном приложение сначала проверяет отдельным соединением (relay и токен из кода,
  `AdminAuth` с ключом из кода, `admin::check_admin_code`) и сохраняет только при успехе.

`clipwire/10` добавляет группы сервера у администратора. Варианты `/9` не менялись, новые
стоят в конце enum (`ClientMsg::ListGroups`, `ClientMsg::DeleteGroup { group }`,
`ServerMsg::Groups`, `ServerMsg::GroupDeleted`, `AdminFail::NoSuchGroup`, `AdminFail::OwnGroup`).
Оба запроса — только после `AdminAuth` и только по `/10`: по старому ALPN сервер считает их
нарушением протокола и закрывает соединение. `ListGroups` → `Groups(Vec<GroupInfo>)`: id группы,
время создания, последний вход любого устройства, число устройств и сколько из них на связи,
элементы, файлы и закрепы с объёмом шифротекста (по всем группам складываются в
`ServerSummary`), есть ли админ и состояние (`GroupState`: обычная, незавершённая смены ключа,
ключ сменён с числом дней до надгробия, заброшенная). Своих имён у групп нет: сервер знает
только id, приложение показывает отпечаток id и пометку «ваша группа» (имена-заметки
администратора — с `/12`, ниже). Список отдаётся
по убыванию активности, не больше 10 000 групп одним кадром (`MAX_LISTED_GROUPS`).
`DeleteGroup` в одной транзакции удаляет всё, что у группы есть (`items`, `blobs`, `cards`,
`devices`, `pins`, `pin_blobs`, `deletes`, `group_config`, `rekeys`), файлы с диска убираются в
фоне, как после смены ключа. Строка группы остаётся надгробием с `deleted_ms` (а также
`rotated_ms` и `tombstone_ms`, поэтому все проверки «ключ сменён» работают как у надгробия), в
списке групп и в пределе групп её нет. Надгробие нужно, чтобы устройство с ключом
администратора не создало группу заново `JoinAsAdmin`, а остальные поняли, что произошло.
Подключённые устройства группы будятся так же, как при смене ключа (`Hub::kick`), и получают
`GroupDeleted`; вход в удалённую группу верным секретом получает то же. Клиенту старее `/10`
сервер вместо этого шлёт `Excluded`: он его знает и останавливает синхронизацию до решения
человека, а незнакомое сообщение оборвало бы соединение, и клиент переподключался бы по кругу.
Новый клиент на `GroupDeleted` перестаёт подключаться и ставит отметку исключения с причиной
(`devices::mark_group_deleted`, вторая строка `deleted` в файле `excluded`); в «Синхронизации»
написано «Группу удалил администратор сервера» и есть только «Выйти из группы». Удалить
группу, в которой состоит само устройство администратора (живую или незавершённую), нельзя:
`AdminFailed(OwnGroup)`, сначала выйти из неё. Группу со сменённым ключом, заброшенную и
незавершённую чужую удалить можно. Приложение спрашивает группы, только если сервер по `/10`;
у старого сервера в карточке «Группы» пояснение «обновите образ сервера».

`clipwire/11` добавляет одноразовые коды создания группы: владелец сервера пускает другого
человека создать свою группу, не давая ему ключа администратора. Варианты `/10` не менялись,
новые стоят в конце enum (`ClientMsg::JoinWithInvite`, `CreateGroupInvite { label, ttl_hours }`,
`ListGroupInvites`, `RevokeGroupInvite { id }`, `ServerMsg::GroupInviteCreated { code_secret, id }`,
`ServerMsg::GroupInvites`, `AdminFail::InviteUnknown`, `InviteUsed`, `InviteExpired`,
`InviteRevoked`, `TooManyInvites`, `NoSuchInvite`). Выпуск, список и отзыв — запросы
администратора: только после `AdminAuth` и только по `/11`. Код `cwgroup1-…` — это сервер
(`ServerInfo` с токеном relay) и 32 случайных байта секрета (`GroupInviteCode`). Сервер хранит
в таблице `group_invites` только SHA-256 секрета, подпись (до 80 символов), время выпуска, срок
(от часа до 90 дней, в приложении 1, 7 или 30 дней), когда и какую группу по коду создали и когда
код отозвали, а также отпечаток токена relay на момент выпуска (`relay_token_fingerprint`,
сам токен в базу не попадает). Поэтому код показывается один раз, при выпуске. `JoinWithInvite { group_id,
join_secret, invite_secret }` первым кадром: если группы нет, `Store::join_limited` в одной
транзакции находит код по хэшу, проверяет, что он не использован, не отозван и не истёк, гасит его
и создаёт группу (предел групп считается как обычно, отказ по пределу откатывает и погашение).
Все записи идут через один замок базы, так что из двух одновременных входов с одним кодом группу
создаст один, второй получит `AdminFailed(InviteUsed)`. Создатель становится админом группы, но
соединение не получает прав администратора сервера. Если группа уже есть, `JoinWithInvite` пускает
только повтор после потерянного ответа: код использован именно для этой группы, выпущен при
текущем токене relay и использован не раньше последней смены токена из клиента. Мусорный,
чужой или неиспользованный код в существующую группу — отказ, иначе такой вход обходил бы
отсечку старых кодов приглашения после смены токена. Неподходящий код —
`AdminFailed(…)` вместо `Joined` и закрытие потока. Действующих кодов не больше 100
(`MAX_ACTIVE_INVITES`), закончившиеся удаляются через 30 дней (`INVITE_KEEP`), всего строк не больше 1000
(`MAX_INVITE_ROWS`: сверх предела при выпуске уходят самые давно закончившиеся, список отдаётся
с тем же пределом). Код с отпечатком не текущего токена relay считается отозванным, так что
смена токена через `CLIPWIRE_RELAY_TOKEN` или правку файла с перезапуском тоже отсекает старые
коды; при запуске такие коды помечаются отозванными. При смене токена из клиента отметка смены и
отзыв действующих кодов идут до записи нового токена. Смена ключа администратора тоже отзывает
все действующие коды. Приложение создаёт группу по такому коду
отдельным соединением с ключом устройства (`admin::create_group_with_invite`) и только после
`Joined` сохраняет состояние, поэтому отказ виден сразу, а секрет нигде не хранится. Ключ
группы и ключ устройства до ответа лежат в черновике `invite-draft.bin` (защищён как
`state.bin`, вместе с SHA-256 секрета кода): повтор с тем же кодом после обрыва берёт те же
ключи и входит в уже созданную группу, черновик удаляется после сохранения состояния. Дальше
движок входит в группу обычным `JoinWithToken`.

`clipwire/12` добавляет имена групп у администратора сервера. Имя — заметка администратора:
сервер хранит его открытым текстом в `groups.name`, устройствам группы оно не уходит, содержимое
групп по-прежнему зашифровано. Варианты `/11` не менялись, новые стоят в конце enum
(`ClientMsg::SetGroupName { group, name }`, `ServerMsg::GroupList(Vec<GroupEntry>)`,
`AdminFail::BadGroupName { max }`). `GroupInfo` не менялся: postcard без версий, и новое поле
сломало бы разбор `Groups` у клиентов `/10` и `/11`. Поэтому имя лежит рядом,
`GroupEntry { info: GroupInfo, name }`, а ответ на `ListGroups`, `DeleteGroup` и `SetGroupName`
зависит от ALPN: соединению `/12` — `GroupList`, старым — прежний `Groups` без имён.
`SetGroupName` — запрос администратора (после `AdminAuth`, только по `/12`, по старому ALPN —
обрыв соединения). Имя проверяет `admin::normalize_group_name`: пробелы по краям убираются,
пустое снимает имя, длиннее 64 символов (`MAX_GROUP_NAME`) или с управляющими символами и
символами направления текста — `AdminFailed(BadGroupName)`. Отдельный вариант, а не
`OutOfRange { key, min, max }`: тот про числовые настройки, а здесь отказ и по длине, и по
символам; новый вариант получает только клиент `/12`, который его знает. Имя ставится и само:
группа, созданная по коду (`JoinWithInvite`), получает подпись кода, обрезанную до 64 символов
(`store::groups::name_from_invite`, в той же транзакции, что гасит код); при смене ключа
`Store::rekey` переносит имя старой группы новой, если у новой своего нет
(`store::groups::inherit_name`). У удалённой группы имя стирается вместе с данными. В лог сервера
имя не пишется. Агент шлёт `SetGroupName` только серверу `/12` (`AdminRequest::min_protocol`),
от сервера `/10`–`/11` список приходит с пустыми именами, и карандаша в приложении нет.

`clipwire/13` добавляет нескольких админов группы. Админы лежат в таблице
`group_admins(group_id, device_id, since_ms)`, первым считается самый ранний. Раньше админ был
один, в столбце `groups.admin_device`. Решений по столбцу сервер больше не принимает, но
держит в нём самого раннего админа, чтобы сервер, откаченный на старую версию, видел понятного
админа. При каждом запуске таблица сверяется со столбцом (`reconcile_legacy`): расхождение
значит, что столбец писала старая версия (база до `/13` или откат), и строки группы заменяются
этим одним админом, а пустой столбец при строках в таблице их удаляет. Так переносится админ
базы старой версии и не теряется то, что старый сервер сделал после отката: передача роли,
новая группа после смены ключа, снятый админ у заброшенной группы. Группы со сменённым ключом и
надгробия сверка не трогает. Все админы равны: любой удаляет устройства, меняет ключ группы,
назначает админом другое устройство группы и снимает роль с любого админа, в том числе с себя.
Новые сообщения стоят в конце enum: `ClientMsg::GrantGroupAdmin { device }`,
`RevokeGroupAdmin { device }`, `GetGroupAdmins`, ответ на все три —
`ServerMsg::GroupAdmins { admins }`, отказ `AdminFail::LastAdmin`. Сервер проверяет всё сам:
назначает и снимает только админ, цель — устройство этой группы (иначе `NoSuchDevice`), группа
живая (не незавершённая и без сменённого ключа), последнего админа снять нельзя. Проверка и
изменение идут в одной транзакции, так что два админа, одновременно снимающие друг друга, не
оставят группу без админа. Остальные устройства группы получают `DevicesChanged`. По старому
ALPN эти сообщения — обрыв соединения.

Старые клиенты `/9`–`/12` работают как раньше. `GetGroupAdmin` отвечает самим спросившим
устройством, если оно админ, иначе самым ранним админом: так старый клиент на любом админе
видит свои кнопки. `TransferGroupAdmin { device }` от админа значит «назначить `device` и снять
себя» одной транзакцией, другие админы остаются. `ClaimGroupAdmin` администратора сервера
добавляет его устройство к админам и прежних не снимает; группа без админов получает админа
при входе с ключом администратора, как раньше.

Удалить устройство из группы можно только сменой ключа, и её начинает админ. При `Rekey`
админами новой группы становятся админы старой, получившие пакет нового ключа, и сам сменивший
ключ (с прежним временем назначения). Исключённые этой сменой роль не уносят. Сменивший ключ
всегда админ и всегда входит в новую группу, поэтому без админов она не остаётся.
Остальные перенесённые админы попадают в устройства новой группы, только когда войдут с новым
ключом. До этого они ничего не могут, а «последний админ» считается только среди админов,
которые в группе состоят: иначе настоящий админ снял бы себя, и группа осталась бы с одним
админом, которого в ней нет. Такого не вошедшего админа можно снять, хотя устройства его в
группе нет. У старой
группы без админов (до 0.5.0) их нет и у новой. Вместе с группой (удаление администратором,
заброшенность, надгробие) удаляются и её админы.

Агент шлёт новые запросы только серверу `/13` (`AdminRequest::min_protocol`), старому сразу
отвечает, что сервер знает одного админа. Приложение спрашивает `GetGroupAdmins` у сервера
`/13` и `GetGroupAdmin` у старого; во втором случае в списке устройств остаётся прежняя
передача роли.

`clipwire/8` добавляет закрепы, общие для группы (`crates/clipwire-core/src/pin.rs`,
`crates/clipwire-server/src/store/pins.rs`). Закреп на сервере — запись под случайным
`pin_id` из двух частей: состояние (`PinState`: `Content::hash`, закреплено ли, подпись до 80
символов, счётчик правок `seq`, время и устройство правки) и содержимое (элемент истории целиком). Обе части
шифруются подключом HKDF `clipwire/v1/pin`, в AAD входят id группы, `pin_id` и вид части, так
что сервер не может подставить часть одного закрепа другому. Открыто сервер видит `pin_id`,
номер правки `rev`, закреплено ли и размеры. `rev` ставит сервер из счётчика правок группы.
`PinSet` несёт `base_rev`, номер, от которого устройство правило, и принимается, только если он
равен текущему `rev` закрепа (0 у нового). Иначе приходит `PinRejected` с текущей записью, и
устройство решает заново. Часы устройств в этом не участвуют. Принятая правка получает
`PinAccepted`, остальным соединениям по `/8` уходит `Pinned`. `PinSet` без содержимого меняет
только состояние (подпись), снятый закреп остаётся записью без содержимого. Устройство
забирает закрепы само: `PinsSince { rev }` отдаёт страницы `Pins` по возрастанию `rev` (до 256
записей и 4 МиБ содержимого со списками файлов), отдельно от истории. Содержимое больше 256 КиБ не кладётся ни в
страницу, ни в `Pinned`, его спрашивают `PinContent`. Рассылка при переполненной очереди
теряется, поэтому курсор по `rev` двигают только страницы. Срока у закрепов нет. Квоты на
группу: `CLIPWIRE_PIN_MAX` закреплённых и `CLIPWIRE_PIN_BYTES` на место закрепов, сверх них
`PinFailed` без разрыва соединения. Снять закреп можно и сверх квоты. Файлы, перечисленные в
`PinSet` (`blobs`), не истекают по сроку, пока закреп не снят. Место закрепов — это записи
закрепов (и снятых) вместе с файлами живых закрепов, по тому же зашифрованному размеру
(`sealed_size`), что у квоты файлов. Квота файлов группы (`CLIPWIRE_BLOB_QUOTA`) считает
только незакреплённые файлы, а предел сервера (`CLIPWIRE_BLOB_TOTAL_QUOTA`) — предел диска, в
нём все живые файлы, закреплённые тоже. Резерв или `Put` файла, который уже есть в
`pin_blobs` группы, сервер проверяет по месту закрепов и пределу сервера, остальные — по
квоте файлов группы и пределу сервера (`Store::blob_begin_with_pins`). `PinSet` сразу считает
уже залитые файлы из своего списка. Файл, заведённый как файл закрепа, помечен
`blobs.pin_only`: когда его перестаёт держать живой закреп (закреп сняли или заменили список
файлов), он сразу истекает и чистится, иначе «закрепил, залил, снял» обходило бы квоту файлов.
Файл, который был обычным до закрепления, после снятия снова обычный со своим временем и
уходит по сроку. При смене ключа закрепы старой группы удаляются вместе с историей.
`GetPinStats` отвечает `PinStats`: число закрепов, место закрепов вместе с файлами и квоты.
`GroupStats`, список групп и сводка сервера считают закреплённые файлы в закрепах, а не в
файлах; формат сообщений тот же. Клиенты 0.7 и старше не принимают в историю новые `blob`
из починенного закрепа: у них такой файл «не найден», пока приложение не обновят. `GroupStats` не менялся: новые поля в нём сломали бы разбор
у клиента, подключённого к старому серверу.

На клиенте закрепы держит книга (`crates/clipwire-agent/src/pins.rs`, файл `pins.bin`,
защищён как `state.bin`): `rev`, открытое состояние и файлы каждой известной записи сервера,
курсор страниц и метка базы сервера, очередь своих правок и отметки «снято только здесь».
Движок (`crates/clipwire-agent/src/sync/pin_engine.rs`) после входа забирает страницы с
курсора, потом выгружает один раз свои прежние закрепы (первое подключение к серверу с
закрепами) и шлёт правки из очереди. Правка лежит на диске, пока сервер её не принял; после
обрыва она уходит снова с тем же `pin_id`, и CAS не даёт завести второй закреп. На
`PinRejected` книга берёт текущую запись и планирует правку заново. Подпись к снятому закрепу
его не возвращает, явное закрепление возвращает. Закрепление живого закрепа подпись группы не
меняет (кроме пустой), её меняет только правка подписи: так повторный импорт Paste и
закрепление после «снять только здесь» не стирают подпись, поправленную на другом устройстве.
Локальная история — только вид: сервис ставит закреп и подпись по событию `Event::Pin`
(`History::apply_pin`), запись без содержимого добавляет из содержимого закрепа. Пока в
очереди лежит своя правка того же хэша, пришедшее в историю не применяется; сервис проверяет
это под замком истории, а команды ставят правку в очередь до записи в историю, поэтому
снятие с сервера не снимет только что поставленный закреп. Когда своя правка ушла (или
оказалась не нужна), история сверяется с книгой. Сообщения сервера о закрепах движок
разбирает асинхронно, обращения к истории идут через `spawn_blocking`.

Файлы закрепа лежат в хранилище группы, там же, где обычные (диск сервера, S3 или SFTP).
Закрепление заливает файлы записи независимо от порога «сразу заливать»: папку архивом, как
при копировании, большие файлы тоже, предел только у сервера (`CLIPWIRE_MAX_FILE_BYTES`).
Если файлов больше порога, окно вставки сначала спрашивает подтверждение с размером
(`history_pin_size`). Залить можно то, чьи байты есть на этом устройстве: свой файл на месте
и не изменился, или скачанная копия в кэше (`pin_files::local_bytes`). Файл, который уже на
сервере, не перезаливается. Остальные получают новые `blob` текущей группы, и правка уходит
с ними в `blobs` раньше заливки, поэтому сервер считает их файлами закрепа. Резерв и
загрузка начинаются после `PinAccepted`. Поэтому получатель может спросить новый файл закрепа раньше, чем источник его зарезервировал: на `NotFound` для файла живого закрепа скачивание не сдаётся сразу, а повторяет запрос до 30 секунд (`blobs::PIN_FILE_WAIT`). Файл, который сервер не принял (больше предела, нет
места закрепов), следующей правкой возвращается в содержимое прежним, а человек видит
причину. Файлы чужой записи в истории следуют за содержимым закрепа (`Event::PinFiles`,
`History::set_pin_files`). Свою запись (`local`) меняет только правка этого устройства, и
только по ней скачанная копия в кэше переезжает в каталог нового `blob`: иначе чужое
содержимое подсунуло бы своей записи `blob` с прямой передачей.

Закреп неполный, если хоть один его файл не лежит в хранилище: нет `blob`, файл для прямой
передачи или сервер не держит его как файл закрепа (нет в `blobs` записи или скачивание
ответило `NotFound`). Так бывает после смены ключа и если файл не залился. Неполный закреп
чинит устройство, у которого есть байты файла: заливает их под новыми `blob` и шлёт правку
поверх текущего `rev` с тем же хэшем, закрепом и подписью, новым содержимым и `seq` на
единицу больше. Автор последней правки закрепа чинит сразу, остальные — после случайной
паузы от 1 до 10 минут (`pin_files::repair_delay`). Перед починкой устройство заново
спрашивает содержимое у сервера (`PinContent`) и чинит то, что ещё не починили. Гонки
разбирает CAS по `rev`: проигравший получает `PinRejected`, а файлы, которые он успел
залить, остаются незакреплёнными и уходят по сроку. За запуск устройство берётся за один
закреп не больше трёх раз, а после отказа сервера в резерве — больше не берётся.

Содержимое закрепа пишет любой участник группы, поэтому починка ему доверяет только в том,
где лежат файлы. Своя ли запись, решает флаг `local` записи истории, а не `origin` из
содержимого. У своей записи путь, имя, папка ли, размер и время берутся из истории
(`pin_files::trusted_files`), исходный файл годится только при точном совпадении размера и
времени, а чужие пути файловой системой не трогаются вовсе: ни stat, ни обход, только кэш
скачанного. Запись, добавленная из содержимого закрепа, всегда чужая, а `origin` этого
устройства в ней обнуляется. Свой файл по чужому закрепу заливается, только если он в
пределах порога «сразу заливать» или это устройство его уже заливало
(`pin_files::may_repair_own`); при пороге 0 — никогда. За запуск движка починка заливает не
больше 1 ГиБ и 50 файлов, и каждый источник один раз (`pin_files::Budget`). Ответ
`PinContent` идёт без `rev`, поэтому перед починкой устройство проверяет, что в содержимом
есть все файлы из записи книги, иначе содержимое старее и починка затёрла бы чужую. Такое
содержимое отмечается вместе с `rev` (`Repairs::checked`) и до новой правки больше не
спрашивается: список файлов `PinSet` открытый, и чужая правка может держать его таким нарочно.
В свою запись истории починка пишет только файлы, которые устройство само залило (номера в
`Event::PinFiles::own`), а если заливка не прошла — возвращает им прежний вид из своей записи,
не из содержимого с сервера.

Снятие закрепа или замена списка его файлов сразу удаляет файлы, заведённые как файлы закрепа
(`pin_only`), которых больше не держит ни один закреп: строки — в той же транзакции
(`Store::set_pin_freeing`), файлы с диска — как при удалении группы (`devices::remove_files`).
Поэтому, когда снятие закрепа принято (своё или пришедшее с другого устройства), движок
забывает в журнале загрузок отметки «залит» у всех файлов этого закрепа
(`UploadedLog::forget`): повторное закрепление заливает их заново, а не считает залитыми.
Обычный файл, который был на сервере до закрепления, при этом просто зальётся ещё раз.

Известные ограничения. Бюджет починки (1 ГиБ и 50 файлов на запуск) инициатор смены ключа с
бóльшим объёмом закрепов исчерпает, остальное дочинится после перезапуска. Своя заливка закрепа
меняет `blob` файла в своей записи; после снятия закрепа файл больше порога удаляется с сервера,
а прямой передачи у записи уже нет, так что другим устройствам он недоступен.

Порядок правок держат `rev` сервера и `seq` внутри запечатанного состояния, а не часы:
запись с большим `rev` принимается всегда, отправитель ставит `seq` на единицу больше
известного. CAS по `rev` не даёт честному серверу принять правку поверх устаревшей, поэтому
`seq` растёт; состояние с меньшим `seq`, чем известное, — возврат старого (`rev` в AAD не
входит), его устройство не применяет и двигает только `rev`. Так же поступает с состоянием,
которое не открылось или не сошлось с открытым `pinned`. `at_ms` — только подсказка, какую
подпись оставить, когда два живых закрепа с одним хэшем (закрепили без связи на двух
устройствах) сводятся к меньшему `pin_id`.

`Pins` несёт `epoch`, случайную метку закрепов группы в базе сервера (`groups.pin_epoch`).
Другая метка значит, что база новая и `rev` пошли заново: книга начинается заново, курсор 0.
Если `PinAccepted` пришёл с номером не больше курсора (базу восстановили из копии), книга тоже
начинается заново. После такого перезапуска, как и после смены ключа, устройство выгружает
не всё закреплённое в истории, а закрепы, живые по данным прежнего сервера, и свою очередь
правок; после смены ключа — только если в новой группе закрепов ещё нет (их перешифровал
инициатор, его книга свежее). Так снятое другими, пока устройство было выключено, не
воскресает.

«Удалить везде» на закрепе сначала снимает закреп и только после `PinAccepted` шлёт записку
об удалении, а записки, пришедшие при входе раньше страниц закрепов (или пока закрепы ждут
разбора), движок придерживает до них: закреплённое записка не удаляет. Обычное удаление
закреплённой записи в группе снимает закреп только здесь, иначе правка с другого устройства
вернула бы запись. При смене ключа инициатор до рассылки пакетов перешифровывает живые
закрепы в новую группу под новыми `pin_id`, отказы сервера (квота) приходят событием; книга
другой группы начинается заново с `rev` 0, очередь правок сохраняется, «снято только здесь»
переходит на хэши. Файлы старой группы сервер и внешнее хранилище удаляют, а заливать до
`Rekey` некуда: новая группа ещё не завершена, и сервер не принимает в неё файлы. Поэтому
перешифрованные закрепы уходят с прежними `blob` и пустым списком файлов, то есть неполными,
и их чинят уже в новой группе. Инициатор — автор этих правок, он чинит сразу после входа с
новым ключом; файлы, которых у него нет, чинят их владельцы после паузы. До починки файл
есть только на устройствах, где он лежит на диске или в кэше.

`PinSet::blobs` перечисляет все файлы закреплённой записи, и в хранилище сервера, и во
внешнем; сервер хранит список (`pin_blobs`) и отдаёт его открыто в `PinRecord::blobs`. Свои
файлы из списка он не удаляет по сроку, а устройства по списку не чистят файлы закрепов во
внешнем хранилище (`external::cleanup`, параметр `kept`), даже если содержимого закрепа у них
нет. Список берётся из книги при запуске сервиса, до первой чистки, и обновляется после
каждой страницы, рассылки и своей правки. Id файлов случайные, о содержимом сервер по ним
ничего не узнаёт. Клиенты до `clipwire/8` о закрепах не знают и чистят внешнее хранилище без
этого списка.

Устройство, которое работало без группы и подключилось, отправляет свою локальную историю
сообщениями `Backfill` с датированными id (UUID v7 от времени копирования). Остальные
кладут такие элементы только в историю, на их место по времени, и буфер не трогают. Сервер
помечает их в базе, чтобы при входе устройство не применило старый элемент к буферу.
При входе в группу устройство вливает в свою историю всё, что пропустило, а в буфер
кладёт только самый свежий элемент, и то если уже бывало в группе.

Сервер шлёт историю по одному элементу (`History`, в конце `HistoryEnd`), и движок
применяет её пачками по мере прихода: по 200 элементов или по 32 МиБ шифротекста, что
наберётся раньше (`HistoryBatcher` в `crates/clipwire-agent/src/sync.rs`). Каждая пачка
уходит в сервис событием `History`, следом движок шлёт `Flush` и, прежде чем отдать
следующую пачку, ждёт ответа: сервис отвечает, когда записал всё до него. Поэтому в памяти
не больше двух пачек и одного кандидата в буфер, сколько бы истории ни держал сервер
(администратор может поднять `history_len` до 100 000). Общего предела на историю при
входе нет. Размер одного элемента ограничен кадром протокола (16 МиБ). Бесконечный поток
от сломанного сервера память не займёт, а на диск попадут только настоящие элементы группы:
подделать шифротекст под ключом группы сервер не может, повторы отсекаются по id.
Кандидат в буфер (последний обычный элемент, которого ещё не видели) переходит через
границы пачек и решается только после `HistoryEnd`, курсор тоже двигается только тогда:
если связь оборвётся посреди истории, при следующем входе она придёт снова, а
уже записанное история пропустит как знакомое. Порядок событий сохраняется: все пачки
`History`, потом кандидат в буфер и `Cursor`, потом записки об удалении.

В буфер ОС попадают только свежие элементы (по `created_at_ms`, оно под шифрованием),
старые идут только в историю. Окна два. Элемент, который сервер разослал сейчас
(`Deliver`), идёт в буфер, если скопирован не раньше 6 часов назад: время берётся с
часов источника, и у источника с отстающими часами узкое окно не пропускало бы в буфер
ничего. Самый свежий элемент истории при входе в группу идёт в буфер, только если
скопирован не раньше 10 минут назад: пропущенное, пока устройство было не на связи, не
должно внезапно подменить то, что человек скопировал у себя. Старый элемент, который
сервер выдал за `Deliver` вместо `Backfill`, в буфер не попадёт, если он старше 6 часов.

Курсор (id последнего виденного элемента, `<state dir>/cursor`) двигается только по
элементам, которые расшифровались, и не дальше чем на 5 минут вперёд от часов
устройства. Элемент с id «из будущего» принимается, но курсор по нему не встаёт:
иначе все новые элементы до той даты считались бы уже виденными. Курсор «из
будущего», сохранённый раньше, при старте сбрасывается.
Почему не P2P сразу: звезда проще, история и офлайн-доставка получаются сами собой, а
текст весит килобайты. Прямые P2P-соединения между устройствами появились на этапе 6, для
файлов: там гнать гигабайты через сервер незачем. Транспорт тот же, iroh
(см. [files-transfer.md](files-transfer.md)).

## Шифрование

- Транспорт уже зашифрован iroh (TLS 1.3 поверх QUIC), relay видит только шифротекст.
- Этого мало: сервер сам является конечной точкой соединения и хранит историю. Поэтому
  каждый элемент дополнительно шифруется **ключом группы** (32 байта) через
  XChaCha20-Poly1305 (крейт `chacha20poly1305`), со случайным nonce на элемент.
- Ключ группы есть только на устройствах. Сервер знает лишь `group_id` (производная от
  ключа через HKDF) и endpoint ID участников.
- `id` и `origin` элемента лежат открыто (серверу они нужны для порядка истории и чтобы
  не слать элемент обратно), но входят в AAD: подмена ломает расшифровку.
- Реализация — `crates/clipwire-core/src/crypto.rs`, там же тесты на чужой ключ и подмену.
- Метаданные, которые сервер всё-таки видит: размер шифротекста, время, какое устройство
  отправило. Тип содержимого лежит внутри шифротекста.

## Добавление устройства

**Этап 2, просто:** первое устройство создаёт группу и показывает **код приглашения**:
строку с адресом сервера, endpoint ID сервера, ключом группы и токеном доступа. Код
вставляется на втором устройстве. Передавать его нужно самому по надёжному каналу:
кто увидел код, тот получил ключ.

PIN или QR с обменом ключом через SPAKE2 (как в CrossPaste) обсуждали и решили не делать:
кода приглашения хватает, а QR имел бы смысл только для телефона.

Доступ к серверу в два слоя:
- **relay** пускает клиентов по общему токену (`access.shared_token`), токен лежит в
  коде приглашения. Пускать relay только зарегистрированные endpoint ID через
  `access.http` нельзя: новому устройству relay нужен ещё до регистрации, чтобы
  достучаться до сервера. Новые группы создаются по коду администратора или одноразовому
  коду создания группы (`clipwire/11`), общий токен relay меняется в разделе «Сервер»;
- **группа:** из ключа группы выводится `JoinSecret`, сервер хранит только его SHA-256.
  Первое устройство создаёт группу, остальные входят, предъявив тот же секрет. Вывести
  ключ шифрования из секрета сервер не может.
- **создание группы:** только входом `JoinAsAdmin` с ключом администратора сервера
  (из кода `cwserver2-…`, сравнивается за постоянное время) или, для новой группы при
  смене ключа, `JoinWithToken` (подробно в описании `clipwire/9` выше). Иначе вход в
  несуществующую группу получает отказ «группы нет; создать группу можно только с
  кодом сервера администратора», `JoinWithToken` с неверным токеном — «неверный код
  сервера». В существующую группу пускают все входы, доступ решает секрет группы. Групп на сервере
  не больше `CLIPWIRE_MAX_GROUPS` (по умолчанию 100), сверх этого новые не создаются.
  В группе не больше `CLIPWIRE_MAX_DEVICES` устройств (по умолчанию 64): новое сверх
  этого получает отказ, уже известные входят как раньше.
  Заброшенные группы сервер чистит сам в цикле чистки: ни одно устройство не входило
  90 дней (`devices.last_seen_ms`, обновляется при каждом входе), нет ни элементов, ни
  файлов, и сейчас никто не подключён. Устройства, карточки, настройки и снятые закрепы
  удаляются, а строка с `join_digest` остаётся с пометкой `groups.idle_ms`. Вход верным
  секретом (любым из трёх входов, без ключа администратора) создаёт такую группу заново,
  как до 0.5.0 это делал первый вход с токеном; админа у неё нет, как у группы до 0.5.0.
  Чужой секрет получает отказ. Заброшенные группы в пределе не считаются.
  Группы со сменённым ключом (`docs/devices.md`) под это правило не попадают: через
  30 дней после смены ключа у них удаляются пакеты нового ключа, карточки и устройства,
  а строка группы остаётся навсегда надгробием. В пределе групп не считаются ни
  надгробия, ни группы со сменённым ключом до них: данных у них уже нет, а цепочка
  «новая группа → `Rekey` → снова» иначе забивала бы предел на 30 дней.

  Как администратору освободить места раньше: поднять предел групп в разделе «Сервер»
  клиента (или `CLIPWIRE_MAX_GROUPS` с перезапуском контейнера). Удалить конкретную группу можно только в базе
  (`<data_dir>/clipwire.db`) при остановленном сервере: `PRAGMA foreign_keys = ON;`,
  потом `DELETE FROM groups WHERE group_id = x'…';` (устройства, элементы и файлы
  удалятся каскадом). Части файлов на диске (`<data_dir>/blobs/<group_id hex>/`)
  тогда надо удалить вручную. В образе нет шелла и `sqlite3`, базу удобнее
  править копией тома на хосте. Если снести весь
  `<data_dir>`, у сервера сменятся ключ и токен, и всем устройствам понадобится новый
  код сервера.

Код приглашения: `clipwire1-` + base32 от `{server_id, relay_url, relay_token, group_key}`
(`crates/clipwire-core/src/invite.rs`).

## Элемент буфера и защита от петель

```
Item { id: uuid v7, origin: endpoint_id, created_at, kind: Text|Image|Files, payload }
```

- Агент, записав чужой элемент в буфер, запоминает его хэш. Если следующее изменение
  буфера даёт тот же хэш, агент его не отправляет.
- Сервер не возвращает элемент устройству-источнику.
- `id` в формате UUID v7 сортируется по времени, им же дедуплицируется история.

## Windows-агент (этап 2)

- Изменения буфера ловим через `AddClipboardFormatListener` (крейт `windows`), без опроса.
- Текст читаем и пишем через `arboard`; картинки, HTML, RTF, файлы (`CF_HDROP`) и
  виртуальные файлы (`CFSTR_FILECONTENTS`) — своим кодом в `clipboard/`.
- Трей и окна — приложение на Tauri (`apps/desktop`), агент стал библиотекой.
- Конфиг и ключи лежат в `%APPDATA%\Clipwire`. Ключи защищены DPAPI, на macOS — связкой
  ключей, на Linux — Secret Service (`secret.rs`).

## Сервер (этап 2)

- Rust, `tokio`, хранилище SQLite (`rusqlite`): группы, устройства, история
  (шифротекст + метаданные).
- Лимиты в конфиге: размер элемента, длина истории, TTL. Значения по умолчанию: 8 МиБ на
  элемент (картинки), 50 элементов, 24 часа.
- В контейнере сервер работает как PID 1 и сам ловит SIGTERM: иначе `docker stop` ждёт
  10 секунд и убивает процесс с кодом 137.
- Образ `gcr.io/distroless/cc-debian12:nonroot`, без шелла. Порты: HTTP relay 3340 (наружу
  через nginx с TLS) и опционально UDP 7843 для прямого QUIC.
- Клиенты знают relay по публичному адресу, а сам сервер подключается к нему локально
  (`http://127.0.0.1:3340`), чтобы не ходить через nginx и обратно. Relay один и тот же
  процесс, поэтому пакеты доходят. Эту схему проверяет `crates/clipwire-server/tests/e2e.rs`:
  клиенты там ходят через `localhost`, сервер через `127.0.0.1`.
- Если первым пришло не `Join`/`JoinWithToken` или секрет неверный, сервер отвечает `Error` и ждёт до
  двух секунд, пока клиент дочитает поток. Иначе соединение закрывается раньше, чем
  клиент увидит причину.
- Пределы против злоупотреблений (`Guards` в `crates/clipwire-server/src/config.rs`):
  - первый кадр до входа в группу — не больше 512 байт, длинный отклоняется по
    префиксу длины, память под него не выделяется. Чтобы `JoinWithToken` в него
    влезал, токен relay (`CLIPWIRE_RELAY_TOKEN` или `relay.token`) не длиннее 256
    байт: с более длинным сервер не запускается и пишет, в чём дело;
  - с одного устройства (endpoint ID) не больше `CLIPWIRE_MAX_DEVICE_CONNS` (4)
    соединений сразу, лишнее получает `Error`;
  - история при входе читается из базы по одному элементу (следующий после уже
    отправленного, по первичному ключу), целиком в памяти она не собирается;
  - общий объём истории всех групп — не больше `CLIPWIRE_HISTORY_TOTAL_BYTES`
    (1 ГиБ, по длине шифротекста). Когда новый элемент не влезает, платит группа с
    наибольшим объёмом истории: у неё удаляется самый старый элемент, и так пока не
    влезет. Если больше всех занимает та группа, что добавляет, она вытесняет свои
    старые элементы, а чужие не трогает; маленькой группе место освобождает самая
    большая. Только что добавленный элемент не удаляется;
  - `Push` и `Backfill` с id не в формате UUID v7 или со временем позже, чем часы
    сервера плюс 24 часа, сервер отбрасывает и пишет в лог (`warn`). Соединение не
    рвётся: иначе агент с убежавшими часами переподключался бы по кругу. Такой id
    встал бы в истории последним навсегда, а история обрезается по id, и он
    вытеснял бы настоящие элементы. Запас в сутки нужен, чтобы устройство со
    спешащими часами не теряло копирования молча; курсор клиентов такой элемент не
    сдвигает (у них свой предел, 5 минут), а место самого свежего в истории он
    занимает не дольше суток.

## Защиты на стороне клиента

- **Метки менеджеров паролей.** Метки исключения, содержимое и владельца буфера агент
  читает за несколько открытий буфера, поэтому сверяет `GetClipboardSequenceNumber` до
  проверки меток и после чтения. Не совпало — перечитывает, до трёх раз, потом
  пропускает это изменение. Если метка `CanIncludeInClipboardHistory` или
  `CanUploadToCloudClipboard` есть, но не прочиталась (буфер не открылся), содержимое
  считается приватным.
- **Картинки.** PNG декодируется через `ImageReader` с пределами: сначала размеры из
  заголовка и проверка `MAX_PIXELS` (64 Мпикс), потом декодирование с пределом памяти.
  Перед записью в буфер размеры картинки сверяются с указанными в элементе.
- **Карточки ссылок** (`apps/desktop/src-tauri/src/link.rs`) не ходят на loopback,
  частные, link-local, CGNAT, ULA, multicast и прочие служебные адреса и на имя
  `localhost`: проверяется исходная ссылка, каждый редирект (их проходится не больше
  пяти) и адрес og:image. Имена
  резолвит свой резолвер и отдаёт клиенту только публичные адреса, так что подключение
  идёт ровно к проверенному IP и DNS rebinding не проходит. Прокси для карточек не
  используется: через прокси имя резолвил бы он.

## Доступ ИИ-инструментов (MCP)

ИИ-клиент (Claude Code, Codex, Cursor, Claude Desktop, VS Code) запускает
`clipwire-desktop --mcp` как stdio-сервер MCP. Это режим того же бинарника, а не отдельная
программа: `main.rs` видит `--mcp` до запуска Tauri и уходит в `mcp_bridge::run()`
(`apps/desktop/src-tauri/src/mcp_bridge/`). Мост не поднимает окон, single-instance и журнала в
stdout (stdout занят MCP, журнал идёт в stderr, уровень в `CLIPWIRE_MCP_LOG`). MCP-сторону
держит крейт `rmcp`.

Мост сам историю не читает и ключей не знает. Каждый вызов инструмента он превращает в один
запрос по локальному каналу к запущенному приложению, а вся политика живёт в приложении
(`apps/desktop/src-tauri/src/mcp/`). Приложение не запущено или доступ выключен — инструмент
возвращает ошибку с понятным текстом.

```
ИИ-клиент ──stdio/MCP──► clipwire-desktop --mcp ──канал (postcard)──► приложение
                          (mcp_bridge)                                (mcp: политика, согласие, журнал)
```

**Канал.** Приложение при старте занимает канал и пишет его адрес одной строкой в
`<папка данных>/mcp/endpoint` (атомарной записью; каталог 0700). Мост находит папку данных по
тому же правилу, что `Paths::resolve()` (`CLIPWIRE_HOME` или стандартная папка), либо по
`--home`.

- Windows: именованный канал `\\.\pipe\clipwire-mcp-<32 hex>`, имя случайное на каждый запуск
  приложения. Первый экземпляр создаётся с `first_pipe_instance(true)`, чтобы чужой процесс не
  занял имя раньше, удалённые клиенты отклоняются, DACL пускает только текущего пользователя и
  SYSTEM.
- macOS и Linux: unix-сокет `<папка данных>/mcp/sock` с правами 0600. Если путь длиннее 100 байт
  (предел `sun_path`), сокет идёт в `$XDG_RUNTIME_DIR/clipwire-<hash8>.sock`, а без неё в
  `/tmp/clipwire-<uid>/<hash8>.sock`; этот каталог проверяется на владельца и права 0700 до и
  после создания, ссылка вместо каталога не принимается.

Если адрес из файла отвечает, канал держит другой экземпляр с той же папкой данных: второй
пишет предупреждение в журнал и работает без MCP. При выходе файл адреса убирается.

**Протокол** — `crates/clipwire-core/src/ai.rs`, `AI_PROTOCOL = 1`. Кадры те же, что у
протокола сервера (postcard с длиной, `proto::write_msg` / `read_msg_limited`), предел кадра
16 МиБ. Один запрос, один ответ, по очереди на соединении. Первое сообщение каждого
соединения `Hello { protocol, client, client_version }`: имя и версия клиента берутся из
`initialize` MCP. Дальше `Search`, `Get`, `Pins`, `Status`, `Save` (в историю и группу, буфер не
трогает) и `Copy` (в системный буфер, а через него в историю и группу). Ответы: `Hello` с
доступом (`Denied`, `Read`, `ReadWrite`), `Items`, `Item`, `Status`, `Saved` и `Error` с кодом
`AiError`. Варианты перечислений кодируются номером, поэтому новые добавляются только в конец, а
несовместимое изменение поднимает `AI_PROTOCOL`. Мост подключается при первом вызове
инструмента и переподключается, если приложение перезапустили.

**Метки элемента.** Две новые метки `ext` в `item.rs`:

- `AI_ORIGIN = 4` (`AiOrigin { client }`): запись положил ИИ-инструмент. Синхронизируется, как
  `SOURCE_APP`; старые версии незнакомую метку хранят и пересылают. Метка держится за
  содержимое: история при склейке её сохраняет, а вставка такой записи из окна вставки несёт её
  дальше (`popup.rs`). В интерфейсе это метка «ИИ · клиент» и полоска цвета `--c-ai`.
- `HISTORY_ONLY = 5` (без данных): элемент от `Save`. Получатель кладёт его в историю, а не в
  буфер (`sync.rs`, `accept`). Метка живёт только в элементе группы: в локальную историю она не
  попадает и при повторной отправке записи снимается (`without_note` в `service.rs`). Версии,
  которые метку не знают, кладут такой элемент в буфер, как обычный.

Запись идёт через `Service::copy_marked` (как `copy`, но с дополнительными метками) и
`Service::save` (без записи в буфер и без звука копирования, возвращает id записи).

**Политика** — `crates/clipwire-agent/src/ai_access.rs`, чистые функции с тестами. Настройки
`Settings.ai` (`AiSettings`) читаются на каждый запрос, так что изменения действуют сразу.
Запись видна, только если выполнено всё:

1. все её виды (`Text`, `Rich`, `Link`, `Image`, `File`, `Folder`) разрешены; файл-картинка
   считается файлом;
2. она не старше окна `history_days` (0 — вся история); закрепы через `Pins` и `Search` с
   `pinned_only` окно не учитывают;
3. программа-источник не в исключениях (`service::is_ignored`);
4. файлы не под правилом «Не отправлять» (`exclusions::blocks_send`);
5. при `hide_secrets` текст не похож на секрет (`looks_secret`): в поиске проверяется карточка
   записи, в `Get` весь текст ещё раз, и скрытая запись отвечает `AiError::Hidden`.

`looks_secret` эвристический: известные префиксы токенов (`sk-`, `ghp_`, `AKIA`, `xoxb-`,
JWT и другие), PEM-ключи, `password=` и похожие пары, пароль в адресе и адреса-ключи
(вебхуки), случайные на вид слова 16–256 символов (не меньше трёх классов символов,
энтропия от 3,5 бита на символ, кроме UUID, хэшей, путей, адресов, почты и версий) и короткий
текст целиком, похожий на пароль. Поиск идёт через `History::scan_visible` со своим ключом
отмены `AI_SCANS`, чтобы не мешать поиску в окне вставки.

**Согласие** (`mcp/consent.rs`, окно `consent`, `apps/desktop/src/consent/Consent.svelte`).
Первый `Hello` от неизвестного имени ставит вопрос в очередь, окно показывает вопросы по
одному. Ответ «Только чтение», «Чтение и запись» (если в настройках разрешена запись) или
«Отказать» запоминается в `settings.ai.clients`; отказ тоже. Нет ответа за 120 с — отказ только
этому соединению, без записи в настройки. `Copy` при `confirm_clipboard` спрашивает ещё раз,
с текстом (первые 4000 символов); после ответа настройки перечитываются, потому что доступ
могли отозвать, пока окно было открыто. Без вопроса `Copy` показывает уведомление. `Save` и
`Copy` требуют и `allow_write`, и доступ клиента `ReadWrite`, иначе `WriteDisabled`.

Клиента узнают по имени из `Hello`, и подтвердить его нечем: любой процесс того же
пользователя ОС может запустить мост и назваться разрешённым клиентом. Токенов на клиента в
первой версии нет, README говорит об этом прямо.

**Журнал обращений.** Таблица `ai_log(id, at_ms, data)` в `history.db`, `data` — `AiLogEntry`
(время, клиент, инструмент, запрос до 80 символов, id записей, результат) в postcard под
XChaCha20-Poly1305 с ключом, выведенным из ключа истории (`AI_LOG_LABEL`). Хранятся последние
1000 строк, `History::clear` журнал не трогает. Настройки показывают последние 100 и обновляют
список по событию `clipwire://ai-log`.

## Память и процессор в простое

Больше всего памяти в клиенте занимают WebView. На Windows это процессы
`msedgewebview2.exe`: один браузерный, GPU, служебные и по процессу рендера на окно. На
macOS это процессы `com.apple.WebKit.WebContent`. Поэтому окна живут так:

- окно вставки создаётся на старте и при закрытии только прячется, чтобы горячая клавиша
  открывала его сразу;
- настройки, пример размера окна вставки и редактор картинок в `tauri.conf.json` помечены
  `"create": false`. Их создаёт `ensure_window` (`apps/desktop/src-tauri/src/lib.rs`), когда
  окно понадобилось, а при закрытии они закрываются насовсем вместе со своим WebView. Пример
  размера закрывается вместе с настройками, редактор закрывается и после сохранения;
- на Windows окно нельзя создавать из главного потока (WebView2 ждёт тот же поток и всё
  встаёт), поэтому `show_settings`, `size_preview` и `editor_open` создают окна в фоновом
  потоке.
- раз окна нет, пока оно закрыто, события ему не доходят. Что нужно увидеть потом, держит
  Rust: найденную версию обновления (`update_found`), события группы, то есть смену ключа,
  неудачу смены и исключение (`group_notices_take`), и id картинки для редактора
  (`editor_pending`). Страница забирает это сама при открытии и после перезагрузки;
- размер, положение, развёрнутость и раздел настроек запоминаются при закрытии в памяти
  процесса и возвращаются при следующем открытии. Прокрутка и недописанные поля теряются.
  Если не сохранена форма хранилища файлов, окно перед закрытием спрашивает.

Остальное в простое:

- значок в трее перерисовывается раз в 0,7 с только при пульсации (подключение, найдено
  обновление). В остальное время такт спит до смены статуса, а тему панели задач Windows
  перечитывает из реестра раз в 30 секунд;
- карточек ссылок в памяти не больше 32: в карточке бывает картинка до 2 МБ;
- скачанное обновление ждёт установки на диске (`update/pending.bin`) и читается только в
  момент установки. Подпись проверяет `Update::install` над прочитанными байтами.

### Как измерить

Сравнивать стоит в одинаковых точках: через пару минут после запуска с `--background`, после
одного показа окна вставки, после открытия и закрытия настроек и редактора, через 10 минут
простоя. Каждую точку лучше снять три раза и взять медиану. Сумма рабочих наборов (WS)
завышена: процессы WebView2 делят страницы памяти. Для сравнения версий честнее сумма
private bytes.

Windows (PowerShell 7): процесс Clipwire и всё его дерево, то есть `msedgewebview2.exe`
браузера и рендеров.

```powershell
$all = Get-CimInstance Win32_Process
$ids = [System.Collections.Generic.HashSet[uint32]]::new()
$all | Where-Object Name -eq 'clipwire-desktop.exe' | ForEach-Object { [void]$ids.Add($_.ProcessId) }
do {
  $added = 0
  foreach ($p in $all) { if ($ids.Contains($p.ParentProcessId) -and $ids.Add($p.ProcessId)) { $added++ } }
} while ($added)
$procs = Get-Process -Id ([uint32[]]$ids) -ErrorAction SilentlyContinue
$procs | Sort-Object WorkingSet64 -Descending |
  Format-Table Id, ProcessName,
    @{ n = 'WS, MB'; e = { [math]::Round($_.WorkingSet64 / 1MB, 1) } },
    @{ n = 'Private, MB'; e = { [math]::Round($_.PrivateMemorySize64 / 1MB, 1) } }
'Total: {0} processes, WS {1:N1} MB, private {2:N1} MB' -f $procs.Count,
  (($procs | Measure-Object WorkingSet64 -Sum).Sum / 1MB),
  (($procs | Measure-Object PrivateMemorySize64 -Sum).Sum / 1MB)
```

Пробуждения процессора в простое видны в Process Explorer, в колонке «Context Switch
Delta» у `clipwire-desktop.exe`.

macOS: процессы WebContent запускает launchd, детьми приложения они не числятся. Их проще
найти сравнением списка до запуска и после. Пока идёт замер, другие программы на WebKit
(Safari, «Почта») лучше не открывать.

```sh
pgrep -f com.apple.WebKit > /tmp/wk.before
open -a Clipwire --args --background; sleep 30
APP=$(pgrep -f 'Clipwire.app/Contents/MacOS' | head -1)
WK=$(pgrep -f com.apple.WebKit | grep -vxFf /tmp/wk.before)
PIDS=$(echo $APP $WK | tr ' ' ',')
ps -o pid=,rss=,comm= -p "$PIDS"
ps -o rss= -p "$PIDS" | awk '{s+=$1} END {printf "RSS total: %.1f MB\n", s/1024}'
for p in $APP $WK; do footprint -p $p | grep -i footprint; done   # как «Память» в Мониторе системы
top -l 6 -s 5 -stats pid,command,cpu,mem,idlew $(printf -- '-pid %s ' $APP $WK)
```

Колонка `idlew` у `top` показывает пробуждения в простое. На маке буфер обмена опрашивается
каждые 250 мс (уведомлений об изменении система не даёт), так что совсем без пробуждений
приложение не бывает.

## Что сознательно отложено

Всё, что здесь стояло на потом, сделано: картинки, файлы и P2P, история в окне вставки,
исключения программ, автообновление ([updates.md](updates.md)). PIN/QR-pairing решили не
делать (см. «Добавление устройства»).

В доступе ИИ-инструментов в первую версию не вошли: запись картинок и файлов, HTTP-транспорт
MCP, свой токен на каждого клиента и правка конфигов ИИ-клиентов из Clipwire.
