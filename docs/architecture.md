# Архитектура Clipwire (черновик к этапу 2)

Статус: предложение, ждёт согласования. Версии сверены 12.11.2026: iroh 1.4.1
(Apache-2.0 / MIT), iroh-relay 1.5.0 в main.

## Компоненты

Один Cargo-workspace:

| Крейт | Что это | Где работает |
|---|---|---|
| `clipwire-core` | Модель элемента буфера, шифрование, формат сообщений, защита от петель | библиотека |
| `clipwire-agent` | Демон в трее: следит за буфером, отправляет и получает элементы | Windows, потом macOS и Linux |
| `clipwire-server` | Почтовый ящик (офлайн-доставка, история с TTL) и встроенный iroh-relay | Docker |

Сервер собран в один бинарник и один контейнер. Relay встроен через
`iroh_relay::server` (фича `server`), отдельного контейнера для него нет. Тому, кто
захочет поднять свой сервер, хватит одного `docker compose up` и записи в nginx.

## Сеть

Все соединения идут через iroh: QUIC с TLS, у каждого устройства своя пара ключей
Ed25519 (endpoint ID). Если UDP пройти не может, iroh сам уходит через relay по
HTTPS/WebSocket, поэтому снаружи достаточно 443 за обратным прокси. Если откроем ещё и
UDP-порт, соединения с сервером пойдут по QUIC напрямую и станут быстрее.

**Этап 2 — схема «звезда»:** агент держит одно соединение с сервером (ALPN
`clipwire/1`). Сервер раздаёт элемент остальным устройствам группы, которые сейчас в
сети, и хранит последние N элементов с TTL для тех, кто офлайн.
Почему не P2P сразу: звезда проще, история и офлайн-доставка получаются сами собой, а
текст весит килобайты. Прямые P2P-соединения между устройствами добавим на этапе 5, для
файлов: там гнать гигабайты через сервер незачем. Транспорт остаётся тем же, iroh.

## Шифрование

- Транспорт уже зашифрован iroh (TLS 1.3 поверх QUIC), relay видит только шифротекст.
- Этого мало: сервер сам является конечной точкой соединения и хранит историю. Поэтому
  каждый элемент дополнительно шифруется **ключом группы** (32 байта) через
  XChaCha20-Poly1305 (крейт `chacha20poly1305`), со случайным nonce на элемент.
- Ключ группы есть только на устройствах. Сервер знает лишь `group_id` (производная от
  ключа через HKDF) и endpoint ID участников.
- `id` и `origin` элемента лежат открыто (серверу они нужны для порядка истории и чтобы
  не слать элемент обратно), но входят в AAD: подмена ломает расшифровку.
- Реализация — `crates/clipwire-core/src/crypto.rs`, там же тесты на чужой ключ и подмену.
- Метаданные, которые сервер всё-таки видит: размер шифротекста, время, какое устройство
  отправило. Тип содержимого лежит внутри шифротекста.

## Добавление устройства

**Этап 2, просто:** первое устройство создаёт группу и показывает **код приглашения**:
строку с адресом сервера, endpoint ID сервера, ключом группы и токеном доступа. Код
вставляется на втором устройстве. Передавать его нужно самому по надёжному каналу:
кто увидел код, тот получил ключ.

**Этап 6, удобно:** короткий PIN или QR и обмен ключом через SPAKE2 между
устройствами напрямую, по примеру CrossPaste. Ключ группы тогда в открытом виде никуда
не передаётся.

Доступ к серверу в два слоя:
- **relay** пускает клиентов по общему токену (`access.shared_token`), токен лежит в
  коде приглашения. Пускать relay только зарегистрированные endpoint ID через
  `access.http` нельзя: новому устройству relay нужен ещё до регистрации, чтобы
  достучаться до сервера. Вернёмся к этому вместе с pairing на этапе 6;
- **группа:** из ключа группы выводится `JoinSecret`, сервер хранит только его SHA-256.
  Первое устройство создаёт группу, остальные входят, предъявив тот же секрет. Вывести
  ключ шифрования из секрета сервер не может.

Код приглашения: `clipwire1-` + base32 от `{server_id, relay_url, relay_token, group_key}`
(`crates/clipwire-core/src/invite.rs`).

## Элемент буфера и защита от петель

```
Item { id: uuid v7, origin: endpoint_id, created_at, kind: Text|Image|Files, payload }
```

- Агент, записав чужой элемент в буфер, запоминает его хэш. Если следующее изменение
  буфера даёт тот же хэш, агент его не отправляет.
- Сервер не возвращает элемент устройству-источнику.
- `id` в формате UUID v7 сортируется по времени, им же дедуплицируется история.

## Windows-агент (этап 2)

- Изменения буфера ловим через `AddClipboardFormatListener` (крейт `windows`), без опроса.
- Текст читаем и пишем через `arboard`, позже понадобятся свои форматы (картинки,
  `CFSTR_FILECONTENTS`).
- Трей через `tray-icon`: «Пауза», «Код приглашения», «Выход».
- Конфиг и ключи лежат в `%APPDATA%\Clipwire`. Ключ группы защищён DPAPI, на macOS
  потом Keychain.

## Сервер (этап 2)

- Rust, `tokio`, хранилище SQLite (`rusqlite`): группы, устройства, история
  (шифротекст + метаданные).
- Лимиты в конфиге: размер элемента, длина истории, TTL. Значения по умолчанию: 1 МиБ на
  элемент для этапа 2, 50 элементов, 24 часа.
- Образ `gcr.io/distroless/cc-debian12:nonroot`, без шелла. Порты: HTTP relay 3340 (наружу
  через nginx с TLS) и опционально UDP 7842 для прямого QUIC.
- Клиенты знают relay по публичному адресу, а сам сервер подключается к нему локально
  (`http://127.0.0.1:3340`), чтобы не ходить через nginx и обратно. Relay один и тот же
  процесс, поэтому пакеты доходят. Эту схему проверяет `crates/clipwire-server/tests/e2e.rs`:
  клиенты там ходят через `localhost`, сервер через `127.0.0.1`.
- Если первым пришло не `Join` или секрет неверный, сервер отвечает `Error` и ждёт до
  двух секунд, пока клиент дочитает поток. Иначе соединение закрывается раньше, чем
  клиент увидит причину.
