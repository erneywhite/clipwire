# Хранение истории

Как устроена локальная история после переделки 0.3: память не растёт вместе с историей.
До неё `History::load_all` расшифровывал все записи при запуске и держал их в памяти целиком,
вместе с картинками и HTML. 35 тыс. записей из Paste — это 163 МБ, с картинками было бы
больше 4 ГБ.

## Цель

- В памяти нет ничего, что растёт с числом записей. Держится только страница окна вставки,
  открытый предпросмотр и маленький кэш значков программ.
- Каждая запись по-прежнему зашифрована ключом истории (`history.key`). Открыто на диске лежит
  ровно то же, что и раньше, плюс ключевой хэш для поиска дублей.
- Поведение для человека не меняется: порядок, дубли, закреплённые, срок хранения, удаление на
  всех устройствах, отправка истории в группу.

## Схема

`PRAGMA user_version = 3`. Две таблицы: тела и карточки.

Таблица `entries` — тела, те же колонки, что у 0.2.x (она читает и пишет их по именам):

| Колонка | Открыто | Что |
|---|---|---|
| `id` | да | `ItemId` (UUID v7), как раньше |
| `seen_ms` | да | когда запись последний раз попала в буфер, как раньше |
| `pinned` | да | как раньше |
| `nonce` | да | nonce тела |
| `thumb_nonce`, `thumb` | нет | миниатюра, как раньше |
| `data` | нет | тело: полная запись (`Entry` в postcard), как раньше. Читается по требованию |

Таблица `cards` — карточки, по строке на запись:

| Колонка | Открыто | Что |
|---|---|---|
| `id`, `seen_ms`, `pinned` | да | копия колонок тела: лента сортируется и фильтруется по ним, не заходя в `entries` |
| `hkey` | да | HMAC-SHA256 от `Content::hash()` на ключе, выведенном из ключа истории. По голому хэшу можно было бы проверять догадки («есть ли в истории `qwerty123`»), по ключевому нельзя |
| `body_nonce` | да | `nonce` тела, из которого собрана карточка |
| `broken` | да | `NULL` у живой строки; у нечитаемой — метка ключа, при котором это выяснилось (8 байт HMAC от постоянной метки, о ключе ничего не говорит) |
| `card_nonce`, `card` | нет | карточка: всё, что нужно строке списка, поиску и служебным проверкам |

Почему карточки в отдельной таблице. В SQLite любая правка строки переписывает её целиком,
вместе с телом на страницах переполнения. Пока карточка лежала в строке тела, каждая починка
или дописывание карточки переписывало и тело: у истории с картинками это гигабайты в WAL и
долгий замок записи. Теперь правка карточки трогает только маленькую строку в `cards`, а обход
ленты читает только эту таблицу: строки в ней небольшие и лежат плотно.

В `entries` миниатюра стоит перед телом: её чтение не проходит по страницам переполнения тела.
Тело и миниатюра — в прежнем формате. Карточка зашифрована с привязкой к `id` и к `nonce` тела
(AAD): чужую карточку на место другой строки не подложить, `body_nonce` не подменить.

Индексы:

- `cards_live (seen_ms DESC, id DESC) WHERE broken IS NULL` — лента и счётчики. Пропуск
  `OFFSET` и `COUNT(*)` идут по индексу и не видят нечитаемых строк;
- `cards_hkey (hkey)` — дубли (не уникальный: при совпадении берётся самая свежая строка);
- `cards_check (id, body_nonce, broken)` и `entries_nonce (id, nonce)` — покрывающие, для
  сверки карточек с телами при открытии (см. ниже);
- `entries_seen (seen_ms)` — чистка по сроку.

Значки программ-источников вынесены в отдельную таблицу `icons(key, nonce, data)`, где `key` —
ключевой хэш байтов значка. Одинаковые значки лежат один раз, а у разных программ с одним
именем exe (`python3`, `Update.exe`) значки не путаются. Ключ значка записи хранится в её
карточке. Раньше значок до 8 КБ лежал в каждой записи. Когда записи удаляются по сроку
хранения, значки, на которые больше не ссылается ни одна карточка, убираются из `icons`
(`History::prune_icons`; ключ значка лежит в зашифрованной карточке, поэтому карточки
обходятся целиком).

Тип записи, признак ссылки и признак файлов в открытые колонки не выносятся: по ним фильтр
работает на расшифрованных карточках.

Отметки об удалении — таблица `tombstones(kid, hkey, at_ms)`, и рядом `marks(name, value)` со
временем последней очистки истории (`cleared_ms`). Обе добавлены без смены `user_version`
(`CREATE TABLE IF NOT EXISTS`), старая версия их не видит и не трогает:

| Колонка | Открыто | Что |
|---|---|---|
| `kid` | да | HMAC от `id` удалённой записи на том же ключе, что `hkey` (с приставкой, вход другой длины, значения не пересекаются с `hkey`). Сам `id` (в нём время копирования) не хранится |
| `hkey` | да | ключевой хэш содержимого, как в `cards` |
| `at_ms` | да | когда удалили |

Зачем они. Дубли ищутся только среди живых строк, и без отметок удалённую запись возвращал
бы сервер: тот же запечатанный элемент историей при входе, `Backfill` (флаг локальной истории
лежит вне шифрования, курсор его не отсекает) или повтором `Deliver`. Злой сервер может это
сделать нарочно, честный — в пределах своего срока хранения при переподключении.

Отметки пишут удаление записи человеком (`History::delete`: одна запись, выделенные, удаление
закреплённого) и удаление запиской с другого устройства (`delete_remote`, время записки, но не
позже своих часов). Очистка по сроку хранения отметок не пишет: удалённое ею старше срока (от
суток), сервер его обычно уже не держит, а вернувшийся старый элемент встанет на своё место по
времени и уйдёт следующей очисткой. Тысячи отметок от неё вытеснили бы отметки удалений,
сделанных человеком. Таблица держится в пределах 20 тыс. строк, самые старые уходят первыми.
«Очистить историю» отметок по строкам не пишет, только время очистки.

## Карточка

Зашифрованная запись от сотни байт до ~9 КБ:

- откуда: устройство, имя устройства, своя или чужая;
- тип (текст, форматированный текст, картинка, файлы, другое), ссылка ли это;
- начало текста для строки списка (400 символов) и текст для поиска: первые 8 КБ в нижнем
  регистре;
- полные размеры текста: символы, строки, байты (для подписи в строке, без чтения тела);
- формат форматированного текста (HTML или RTF);
- размеры картинки;
- для файлов — полный список `FileRef` (имена, пути, размеры, blob, p2p): он маленький и нужен
  проверкам `in_history`, `local_p2p_file` и чистке кэша;
- программа-источник: имя, exe и ключ значка. Сведения по меткам (`ext`) лежат в карточке
  целиком, без значка: подъём записи при повторном копировании не читает тело;
- простой хэш содержимого (`Content::hash()`): по нему «удалить на всех устройствах» уходит в
  группу без чтения тела.

Поиск по тексту идёт по первым 8 КБ. В очень длинном тексте совпадение дальше 8 КБ не найдётся;
это сознательная цена за то, что поиск не читает тела. Другая цена — место: у текстовой истории
карточки занимают примерно столько же, сколько тела (текст для поиска и начало для строки
списка — копия текста). 100 тыс. записей из нагрузочной проверки: база 0.2 — 107 МБ, новая —
около 255 МБ.

## Как работают операции

- **Лента и поиск.** Строки `cards` читаются по `seen_ms DESC, id DESC`, расшифровываются только
  карточки, фильтры (закреплённые, тип, запрос) применяются к ним. Как только набрано
  `offset + limit` совпадений, чтение останавливается. Частые запросы находятся быстро, весь
  архив перебирают только редкие. Поэтому окно вставки отправляет запрос через 150 мс после
  последней нажатой клавиши, а не на каждую букву. Enter, стрелки, Delete, Ctrl+1…9 и другие
  клавиши списка, нажатые до паузы или пока новый список ещё читается, ждут конца чтения и
  срабатывают по новому списку. Если за это время окно спрятали или открыли заново, клавиша
  не срабатывает.
- **Добавление и дубли.** Дубль ищется по `hkey`. Совпадение поднимает существующую строку
  наверх, как раньше. Если строка с таким `id` уже есть, это тоже подъём, а не вторая запись.
  Тело и карточка пишутся в одной транзакции, миниатюра — в той же вставке тела.
- **Срок хранения.** Id старых незакреплённых строк берутся из `entries` по `entries_seen`, строки
  удаляются из обеих таблиц в одной транзакции.
- **Удаление с других устройств.** Пришедшие простые хэши переводятся в ключевые, строки с
  ними удаляются из обеих таблиц, на каждую пишется отметка об удалении.
- **Чужое из группы после удаления.** Элемент группы (история при входе, `Backfill`, `Deliver`)
  не вливается, если есть отметка с его `id` или с его `hkey` и временем удаления не раньше
  времени копирования элемента (`created_at_ms`, под шифрованием, сервер его не подделает), а
  также если он скопирован не позже последней очистки истории. Своё копирование того же
  содержимого здесь проверку не проходит вовсе, чужое копирование после удаления — новое и
  приходит. Разосланный элемент с `id`, который уже есть в истории, не трогает ни историю, ни
  буфер: это повтор (у элемента с `id` из будущего курсор не двигается, и сервер мог бы слать
  его снова). Закреп группы возвращает запись, только если его правили после удаления
  (`History::buried_for_pin`); очистка истории закрепы не задевает.
- **Метка «только здесь».** Своё копирование, которое в группе не ушло (пауза, «Что отправлять»,
  «Не отправлять»), получает метку `ext::LOCAL_ONLY` (6) в сведениях записи, как подпись: она в
  теле и в карточке, схема не меняется. По ней починка чужого закрепа не заливает файлы записи и
  после того, как причина прошла, а локальная история не уходит с ней в новую группу. Метку
  снимает только сам человек: копирование той же записи, когда отправлять можно, или закрепление.
  В элементы группы и в содержимое закрепов метка не кладётся, пришедшая отбрасывается.
- **Отправка истории в группу.** 50 последних своих записей, тела читаются только для них.
- **Счётчики.** `COUNT(*)` по индексу `cards`, нечитаемые строки не считаются.
- **Чистка кэша файлов и проверки путей.** Перебор карточек файлов, без тел, одним проходом
  за блобами и путями сразу. Что сейчас качается, берётся после перебора: запись, пришедшая во
  время перебора, уже качается и не попадёт под удаление. Чистки не копятся: просьбы, пришедшие
  во время чистки, сливаются в один повтор после неё.
- **Закрепление.** Меняет колонки и переписывает тело (одно перешифрование, у картинки это
  мегабайты и миллисекунды): старая версия после отката берёт закрепление из тела.
- **Подпись.** Лежит в сведениях записи меткой `ext::NOTE` (3), поэтому попадает и в тело, и в
  карточку: строка списка и поиск видят её без чтения тела, схема и миграция не меняются.
  Подпись бывает только у закреплённого, открепление её стирает. В элементы группы подпись не
  кладётся (она ходит состоянием закрепа), пришедшая в элементе отбрасывается. Старая версия
  после отката метку не знает и просто её хранит.
- **Закреп с другого устройства.** `apply_pin` ищет запись по простому хэшу (переводит его в
  ключевой) и ставит закреп и подпись; записи нет — добавляет её из содержимого закрепа на своё
  место по времени. Какой `pin_id` и `rev` у закрепа, история не знает: это книга закрепов
  (`pins.bin`, `crates/clipwire-agent/src/pins.rs`), связь — по хэшу.

Все транзакции записи берут замок сразу (`BEGIN IMMEDIATE`). Отложенная транзакция, которая
сначала читает (ищет дубль), а потом пишет, падала бы с `SQLITE_BUSY_SNAPSHOT`, если между
чтением и записью успел записать другой процесс, и копирование терялось бы.

## Второе соединение

Чтение, которое перебирает все карточки (поиск редкого слова, вкладка «Картинки» или «Файлы»
при немногих совпадениях, проверки путей, прямая отдача файла другому устройству, чистка
кэша), идёт через второе соединение с той же базой (`HistoryReader`), открытое только для
чтения. В режиме WAL читатель не ждёт записи, а запись не ждёт его, поэтому новое копирование
и окно вставки не стоят, пока идёт обход. Такое чтение запускается отдельным потоком, не на
потоках асинхронных задач.

Одновременно идут не больше двух таких чтений, остальные ждут. Поиск, устаревший из-за нового
запроса с другим текстом или вкладкой, бросает обход (проверка раз в 64 карточки) и отдаёт
пустую страницу: окно её всё равно отбрасывает по своему номеру списка. Запросы с тем же
текстом (следующая страница, перечитывание после новой записи) друг друга не останавливают.

Если при чтении карточка не открылась, читатель берёт тело и отдаёт поправку соединению
записи. Тот пишет её сразу после чтения, если свободен, иначе — в начале своей следующей
транзакции. Читатель сам ничего не пишет. Поправка условная: пишется, только если тело с тех
пор не переписали. Один обход читает не больше 100 тел вместо неоткрывшихся карточек, дальше
такие строки в нём пропускаются: после сверки при открытии их не бывает, а без предела поиск
по сломанной истории читал бы все тела.

## Нечитаемые строки

Строка помечается нечитаемой (`broken`), только если и карточка, и тело не проходят проверку
подлинности (чужой ключ, порча). Тело, которое расшифровалось, но не разобралось (запись более
новой версии), строку не помечает: её просто пропускают. Лента, поиск, счётчики и проверки
файлов нечитаемых строк не видят и тело больше не читают.

Пометка обратима. В `broken` лежит метка ключа, и при открытии строки, помеченные при другом
ключе, перепроверяются: вернули прежний `history.key` — записи вернулись. Строку с тем же `id`,
пришедшую из истории группы, нечитаемая не блокирует: пришедшая её заменяет. То же содержимое,
скопированное снова, становится новой записью. Удаляет нечитаемые строки чистка по сроку и
«Очистить историю».

## Сверка при открытии

При каждом открытии карточки сверяются с телами за один проход:

- карточки, у которых нет тела (запись удалила старая версия после отката), удаляются;
- тела без карточки (записала старая версия) и тела, у которых `nonce` не тот, из которого
  собрана карточка (переписала старая версия), получают новую карточку. Ключ значка берётся из
  прежней карточки, если в теле значка нет: старая версия переписывает тело без значка,
  вынутого в `icons`;
- строки, помеченные нечитаемыми при другом ключе, перепроверяются.

Сравниваются только покрывающие индексы `entries_nonce` и `cards_check` (на 100 тыс. записей —
около 11 МБ), тела читаются лишь у найденных строк. Пишутся только карточки, пачками по 500
строк. Ключевые хэши таких строк поправлены сразу при запуске, а не когда до строки дойдёт
обход.

## Переход со старой базы

С 0.2.x (схема 0) и с базы ветки разработки (схема 2, карточка в строке тела) при первом
запуске рядом собирается новая база `history.db.v3-tmp`:

- тела (`nonce`, `data`) и миниатюры копируются как есть, без перешифрования;
- карточки собираются в том же проходе. Карточка схемы 2 или запасного режима переносится
  готовой, если открывается этим телом; иначе собирается из тела. Значок из тела 0.2
  копируется в `icons`. Так каждое тело пишется один раз;
- строки идут в порядке времени: карточки ленты ложатся в файл подряд;
- индексы строятся в конце.

Затем число строк в новой базе сверяется со старой, и новый файл одним переименованием
заменяет `history.db`. Копии старой базы не остаётся: до переименования на месте старый файл,
после — новый. Файлы перехода ветки разработки (`history.db.bak-v1`, `history.db.v2-tmp`)
удаляются при открытии; если тот переход оборвался между двумя переименованиями, собранная
база сначала встаёт на место. Копия `bak-v1` без самой `history.db` на её место не встаёт:
историю удалили.

Сбои перехода не мешают запуску:

- новая база не собралась (мало места, ошибка) — недособранный файл удаляется, старая база
  открывается в запасном режиме: рядом со старой таблицей тел создаётся `cards` (меняется только
  схема, тела не переписываются), и сверка при открытии собирает карточки. Всё работает, только
  миниатюра картинки в базе 0.2 лежит после тела и читается через него. Версия схемы остаётся
  старой, следующий запуск пробует перейти снова и переносит готовые карточки;
- базу держит другой процесс (консольный клиент): после закрытия своего соединения остался
  `history.db-wal`. Файл под чужим соединением не заменяется, запуск идёт в запасном режиме;
- процесс умер посреди сборки — `v3-tmp` удаляется и собирается заново при следующем запуске.

Если не создаётся и таблица запасного режима (база только для чтения, диск отказал), история
не открывается, как и раньше.

## Место на диске и WAL

- Переход: на время сборки нужно место ещё на одну базу (старая и новая рядом), новая больше
  старой из-за карточек (см. «Карточка»). У новой базы нет журнала (при сбое её собирают
  заново), старая только читается, WAL не растёт. Новый файл плотный, `VACUUM` не нужен.
- Сверка и поправки карточек пишут в WAL только карточки: сотни байт, у длинного текста до
  ~9 КБ на строку.
- Запись, подъём, правка и закрепление пишут в WAL тело целиком (у картинки — мегабайты), как
  и раньше. Миниатюра, добавленная позже (скачанный файл-картинка), переписывает строку тела,
  но у файлов тело маленькое.
- Чистка по сроку пишет в WAL освобождённые страницы.
- После большой транзакции WAL урезается до 64 МБ (`journal_size_limit`), а не остаётся её
  размера.

## Откат на старую версию

Откат на 0.2.x поддерживается, с оговорками:

- старая версия читает и пишет таблицу `entries`, а время и закрепление в теле всегда
  актуальны: их переписывают подъём, правка и закрепление;
- у записей, записанных новой версией, значок программы вынут из тела в `icons`, старая версия
  покажет их без значка;
- что старая версия поменяла, новая после обновления подхватит при первом же открытии (см.
  «Сверка при открытии»): новые записи получат карточки, у поднятых и правленых карточки
  пересоберутся с прежним значком, удалённые уйдут и из `cards`.

## Нагрузочная проверка

`cargo test -p clipwire-agent --release --lib history::tests::bench -- --ignored --nocapture`,
100 тыс. записей (тексты, форматированный текст, файлы, 50 картинок), база 257 МБ:

|---|---|
| Заполнение | 5,9 с |
| Открытие со сверкой карточек | 70 мс |
| Первая страница (200) | 1,8 мс |
| Страница на глубине 50 000 | 4,7 мс |
| Поиск, совпадение у верха | 0,3 мс |
| Поиск, 200 совпадений у верха | 1,7 мс |
| Поиск редкого слова (вся история) | 436 мс |
| Поиск без совпадений (все карточки) | 434 мс |

## Настройки SQLite

`journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000` (консольный клиент и
приложение могут открыть одну базу), кэш страниц ограничен (`cache_size = -4000`, около 4 МБ),
`journal_size_limit = 64 МБ`, `mmap` не включается.
