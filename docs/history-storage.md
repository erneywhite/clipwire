# Хранение истории

Как устроена локальная история после переделки 0.3: память не растёт вместе с историей.
До неё `History::load_all` расшифровывал все записи при запуске и держал их в памяти целиком,
вместе с картинками и HTML. 35 тыс. записей из Paste — это 163 МБ, с картинками было бы
больше 4 ГБ.

## Цель

- В памяти нет ничего, что растёт с числом записей. Держится только страница окна вставки,
  открытый предпросмотр и маленький кэш значков программ.
- Каждая запись по-прежнему зашифрована ключом истории (`history.key`). Открыто на диске лежит
  ровно то же, что и раньше, плюс ключевой хэш для поиска дублей.
- Поведение для человека не меняется: порядок, дубли, закреплённые, срок хранения, удаление на
  всех устройствах, отправка истории в группу.

## Схема

`PRAGMA user_version = 2`. Таблица `entries`:

| Колонка | Открыто | Что |
|---|---|---|
| `id` | да | `ItemId` (UUID v7), как раньше |
| `seen_ms` | да | когда запись последний раз попала в буфер, как раньше |
| `pinned` | да | как раньше |
| `hkey` | да | HMAC-SHA256 от `Content::hash()` на ключе, выведенном из ключа истории. По голому хэшу можно было бы проверять догадки («есть ли в истории `qwerty123`»), по ключевому нельзя |
| `card_nonce`, `card` | нет | карточка: всё, что нужно строке списка, поиску и служебным проверкам |
| `nonce`, `data` | нет | тело: полная запись (`Entry` в postcard), как раньше. Читается по требованию |
| `thumb_nonce`, `thumb` | нет | миниатюра, как раньше |

Порядок колонок в таблице тот же, что в списке выше: тело последним. SQLite кладёт строку
одним куском, и колонки после большого тела читались бы через его страницы переполнения; так
карточки и миниатюры читаются без прохода по телам. Карточка зашифрована с привязкой к `id` и
к `nonce` тела (AAD): чужую карточку на место другой строки не подложить, а если тело переписали
без карточки (старая версия после отката), карточка перестаёт открываться и пересобирается из
тела. Тело и миниатюра — в прежнем формате.

Строка, у которой не читаются ни карточка, ни тело (чужой ключ, порча), помечается пустой
карточкой `card = X''`, без `hkey`. Лента, поиск, счётчики и проверки файлов её не видят и тело
больше не читают, дописывание карточек её тоже не трогает. Удаляет такие строки чистка по сроку
и «Очистить историю».

Индексы: `(seen_ms DESC, id DESC)` для чистки по сроку; частичный `(seen_ms DESC, id DESC)
WHERE card IS NOT X''` для ленты и счётчиков (пропуск `OFFSET` и `COUNT(*)` идут по индексу и
не видят битых строк); `hkey` для дублей (не уникальный: при совпадении берётся самая свежая
строка) и частичный `id WHERE card IS NULL`, чтобы проверка недописанных карточек при открытии
ничего не стоила.

Значки программ-источников вынесены в отдельную таблицу `icons(key, nonce, data)`, где `key` —
ключевой хэш байтов значка. Одинаковые значки лежат один раз, а у разных программ с одним
именем exe (`python3`, `Update.exe`) значки не путаются. Ключ значка записи хранится в её
карточке. Раньше значок до 8 КБ лежал в каждой записи.

Тип записи, признак ссылки и признак файлов в открытые колонки не выносятся: по ним фильтр
работает на расшифрованных карточках.

## Карточка

Зашифрованная запись в несколько сотен байт:

- откуда: устройство, имя устройства, своя или чужая;
- тип (текст, форматированный текст, картинка, файлы, другое), ссылка ли это;
- начало текста для строки списка (400 символов) и текст для поиска: первые 8 КБ в нижнем
  регистре;
- полные размеры текста: символы, строки, байты (для подписи в строке, без чтения тела);
- формат форматированного текста (HTML или RTF);
- размеры картинки;
- для файлов — полный список `FileRef` (имена, пути, размеры, blob, p2p): он маленький и нужен
  проверкам `in_history`, `local_p2p_file` и чистке кэша;
- программа-источник: имя, exe и ключ значка. Сведения по меткам (`ext`) лежат в карточке
  целиком, без значка: подъём записи при повторном копировании не читает тело;
- простой хэш содержимого (`Content::hash()`): по нему «удалить на всех устройствах» уходит в
  группу без чтения тела.

Поиск по тексту идёт по первым 8 КБ. В очень длинном тексте совпадение дальше 8 КБ не найдётся;
это сознательная цена за то, что поиск не читает тела.

## Как работают операции

- **Лента и поиск.** Строки читаются по `seen_ms DESC, id DESC` пачками, расшифровываются
  только карточки, фильтры (закреплённые, тип, запрос) применяются к ним. Как только набрано
  `offset + limit` совпадений, чтение останавливается. Частые запросы находятся быстро, весь
  архив перебирают только редкие. Поэтому окно вставки отправляет запрос через 150 мс после
  последней нажатой клавиши, а не на каждую букву; Enter, стрелки и другие клавиши списка
  сначала дожидаются нового списка.
- **Добавление и дубли.** Дубль ищется по `hkey`. Совпадение поднимает существующую строку
  наверх, как раньше. Если строка с таким `id` уже есть, это тоже подъём, а не вторая запись.
- **Срок хранения.** Один `DELETE ... WHERE pinned = 0 AND seen_ms < ?` в транзакции.
- **Удаление с других устройств.** Пришедшие простые хэши переводятся в ключевые и удаляются
  по `hkey`.
- **Отправка истории в группу.** 50 последних своих записей, тела читаются только для них.
- **Счётчики.** `COUNT(*)` по частичному индексу, битые строки не считаются.
- **Чистка кэша файлов и проверки путей.** Перебор карточек файлов, без тел, одним проходом
  за блобами и путями сразу.
- **Закрепление.** Меняет колонку и переписывает тело (одно перешифрование, у картинки это
  мегабайты и миллисекунды): старая версия после отката берёт закрепление из тела.

Чтение, которое перебирает все карточки (поиск редкого слова, вкладка «Картинки» или «Файлы»
при немногих совпадениях, проверки путей, прямая отдача файла другому устройству, чистка
кэша), идёт через второе соединение с той же базой (`HistoryReader`). В режиме WAL читатель не
ждёт записи, а запись не ждёт его, поэтому новое копирование и окно вставки не стоят, пока идёт
обход. Такое чтение запускается отдельным потоком, не на потоках асинхронных задач. На 100 тыс.
записей полный обход занимает около полусекунды.

Если при чтении карточка не открылась, а тело читается, карточка пересобирается из тела и
записывается сразу после обхода. Если не читается и тело, строка помечается битой. Обе
поправки условные: пишутся, только если тело с тех пор не переписали.

## Переход со старой базы

При первом запуске новой версии рядом собирается новая база `history.db.v2-tmp`: та же таблица,
но тело последней колонкой. Тела (`nonce`, `data`) копируются как есть, без перешифрования. Затем
старый файл переименовывается в `history.db.bak-v1`, а новый встаёт на место `history.db`.
Старый файл и служит копией на случай сбоя, отдельной копии нет.

После этого каждая строка без карточки получает `card` и `hkey`, значок из тела копируется в
`icons`. Карточки дописываются пачками по 500 строк в транзакциях. Сбой пачки пишется в журнал
и не мешает запуску: недоделанные строки догонятся при следующем запуске, а читающий код до тех
пор берёт данные из тела. Строки, у которых не читается и тело, помечаются битыми (см. «Схема»)
и больше не перебираются.

Копия `history.db.bak-v1` удаляется, как только все карточки дописаны без ошибок, обычно в том
же запуске. Иначе в ней остались бы записи, удалённые потом вручную, «на всех устройствах» или
по сроку. «Очистить историю» тоже удаляет копию, если она ещё лежит.

Сбои перехода не мешают запуску:

- новая база не собралась (мало места, ошибка) — недособранный файл удаляется, старая база
  открывается в запасном режиме: колонки карточек добавляются в конец старой таблицы (меняется
  только схема, данные не копируются). Всё работает, только чтение карточки большой записи
  проходит и по её телу. Версия схемы остаётся старой, следующий запуск пробует перейти снова и
  переносит уже дописанные карточки;
- базу держит другой процесс (консольный клиент): после закрытия своего соединения остался
  `history.db-wal`. Файл под чужим соединением не переименовывается, запуск идёт в запасном
  режиме;
- процесс умер посреди сборки — `v2-tmp` удаляется и собирается заново при следующем запуске;
- процесс умер между двумя переименованиями (`history.db` нет, есть `v2-tmp` и `bak-v1`) — при
  следующем запуске новая база встаёт на место.

Если не добавляются и колонки запасного режима (база только для чтения, диск отказал), история
не открывается, как и раньше.

Место на диске: во время сборки нужна ещё одна база того же размера (старый файл и новый рядом).
У новой базы нет журнала (при сбое её собирают заново), старая только читается, поэтому WAL не
растёт. Новый файл плотный, `VACUUM` после перехода не нужен. Пока дописываются карточки, рядом
лежит `bak-v1` того же размера; WAL растёт на объём карточек (сотни байт на запись). Потом
остаётся одна база.

## Откат на старую версию

Откат на 0.2.x поддерживается, с оговорками:

- старая версия читает тела, а время и закрепление в теле всегда актуальны: их переписывают
  подъём, правка и закрепление;
- у записей, записанных новой версией, значок программы вынут из тела в `icons`, старая версия
  покажет их без значка;
- что старая версия поменяла, новая после обновления подхватит: новые строки без карточки
  получат её при запуске, у поднятых или правленых карточка перестанет открываться (она
  привязана к `nonce` тела) и пересоберётся из тела при первом чтении.

## Настройки SQLite

`journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000` (консольный клиент и
приложение могут открыть одну базу), кэш страниц ограничен (`cache_size = -4000`, около 4 МБ),
`mmap` не включается.
