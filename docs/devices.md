# Устройства группы, смена ключа и сведения об источнике

Основа уже есть и без согласования не меняется:

- `crates/clipwire-core/src/device.rs`: `DeviceCard`, `GroupKey::seal_card` и
  `open_card` (подпись Ed25519 ключом устройства + шифрование ключом группы),
  `rekey_secret` и `rekey_public` (X25519 из ключа устройства через HKDF),
  `seal_rekey` и `open_rekey` (пакет нового ключа для одного устройства),
  `device_id`.
- `crates/clipwire-core/src/proto.rs`: `ClientMsg::PublishCard`,
  `ClientMsg::ListDevices`, `ClientMsg::Rekey { new_group, envelopes }`,
  `ServerMsg::Devices(Vec<DeviceEntry>)`, `ServerMsg::Rekeyed { envelope }`,
  `ServerMsg::Excluded`.
- `crates/clipwire-core/src/item.rs`: `Item.ext: Vec<Ext>` (метка + байты),
  трейт `ExtList`, метка `ext::SOURCE_APP` и `SourceApp`. Элементы без `ext`
  читаются (`decode_item` → `ItemV3`).

## Карточки устройств

- После входа в группу агент публикует свою карточку (`PublishCard`): имя из
  настроек, ОС, `rekey_public(device_key)`, время выпуска. При смене имени
  устройства — заново.
- Сервер хранит последнюю карточку каждого устройства группы (по `DeviceId`
  соединения, не по содержимому) и отдаёт список на `ListDevices`:
  `DeviceEntry { device, card, last_seen_ms, online }`. Карточку больше 4 КБ не
  принимает.
- Клиент открывает каждую карточку `open_card(device, card)`. Не открылась или
  нет карточки (старая версия) — устройство показывается как «неизвестное
  устройство» с отпечатком id и в смене ключа участвовать не может (ему нечем
  передать новый ключ).

## Смена ключа

Запускает любой админ группы (с сервера 0.5.0; в группе без админа — любое
устройство): «Удалить устройство» (смена ключа без него) или «Сменить ключ
группы» (все остаются). Админы, получившие новый ключ, остаются админами
новой группы, удалённое устройство роль теряет (`docs/architecture.md`,
`clipwire/13`).

1. Человек на устройстве R видит в диалоге список получателей нового ключа
   и подтверждает его. Устройство R берёт свежий список устройств, проверяет
   карточки, исключает удаляемые и сверяет остальных с подтверждённым
   набором: устройство с карточкой, которого человек не видел, отменяет
   смену (см. «Подтверждённые получатели»).
2. Создаёт новый ключ `K2`, входит в новую группу (`JoinWithToken` на том же
   сервере: ключа администратора сервера для этого не нужно, сервер создаёт
   новую группу по праву сменить ключ старой), публикует там свою карточку.
   Входит всегда с токеном, даже если ключ администратора есть: такая группа
   «незавершённая» (`pending_by` = R), и только её сервер принимает новой
   группой в `Rekey`, причём R должно быть в ней одно. До `Rekey` в ней
   можно только карточку, настройки и закрепы группы, без элементов и файлов.
   Админ новой группы после `Rekey` — админ старой. Одно устройство меняет
   ключ не чаще 10 раз в сутки.
3. Для каждого остающегося устройства D (кроме себя) — `seal_rekey(K2, D,
   D.rekey_pub, old_group_id)`, отправляет `Rekey { new_group, envelopes }` в
   старую группу.
4. Сервер в той же транзакции: помечает старую группу «ключ сменён» (ссылка на
   новую, время), сохраняет пакеты по устройствам, удаляет элементы истории и
   файлы старой группы, подключённым к старой группе устройствам шлёт их
   `Rekeyed { envelope }` или `Excluded` и закрывает их соединения.
5. Устройство, входящее в старую группу позже, получает только свой
   `Rekeyed` или `Excluded` (по `DeviceId` соединения). Пакеты, карточки и
   устройства старой группы живут 30 дней, потом удаляются; строка группы
   остаётся надгробием, и вход в неё дальше получает только `Excluded`.
6. Получив `Rekeyed`, устройство делает `open_rekey(device_key, old, envelope)`
   и сверяет инициатора с проверенными карточками группы. Свой пакет (ключ
   сменило это же устройство) принимается сразу: новое состояние (тот же
   сервер, новый ключ), перезапуск движка, вход в новую группу, карточка.
   Пакет от другого знакомого устройства сам не принимается: синхронизация
   останавливается, и человек отвечает, перейти на новый ключ или нет (см.
   «Подтверждение на остальных устройствах»). Код приглашения меняется.
   `Excluded`, не открывшийся пакет или незнакомый инициатор — устройство
   помечается исключённым: синхронизация остановлена, ключ и история на месте,
   человек выбирает «Выйти из группы» или «Попробовать снова».
7. Повторный `Rekey` в группу, где ключ уже сменён, — отказ.

### Подтверждённые получатели

Список устройств приходит с сервера, и между «человек посмотрел список» и
«ключ разослан» он может измениться. Исключаемое устройство знает ключ
группы и токен relay, поэтому может заранее войти в группу вторым
идентификатором с настоящей карточкой, хоть под именем соседнего ноутбука.
Сервер, если он заодно, может показать такое устройство только в том ответе,
который движок запрашивает внутри смены ключа. Если бы новый ключ уходил
всем из свежего списка, он достался бы и такому устройству.

Поэтому новый ключ получают только те, кого человек видел:

- Диалог подтверждения показывает получателей: имя, ОС, отпечаток и когда
  устройство появилось. Время появления — по записям этого клиента
  (`devices.bin`, первое знакомство с карточкой), а не со слов сервера и не
  из карточки. Устройства, впервые увиденные меньше суток назад, выделены.
  Выделены и устройства с одинаковым именем: имя устройство выбирает само,
  а войти вторым идентификатором можно и заранее, за несколько дней.
- У каждого получателя галочка. Снятая галочка исключает устройство вместе
  с удаляемым: одной сменой ключа можно убрать несколько устройств. Без
  этого участник с двумя идентификаторами всегда оставался бы в группе
  хотя бы одним.
- Список в диалоге — снимок на момент открытия. Он не обновляется под рукой,
  и в команду уходят id именно из него: `confirmed` (с галочкой) и `remove`
  (удаляемое и те, с кого галочку сняли).
- Движок строит план только по `confirmed` (`devices::plan_rekey`). Если в
  свежем списке сервера есть устройство с карточкой, которого нет ни в
  `confirmed`, ни в `remove`, смена отменяется до того, как собран хоть
  один пакет: «В группе появилось новое устройство. Проверьте список
  получателей и подтвердите смену ключа заново». Интерфейс закрывает
  диалог и перечитывает список.
- Подтверждённое устройство, которого в свежем списке уже нет, ключ не
  получает и смену не отменяет. Устройства без карточки, как и раньше,
  остаются без ключа: передать его им нечем.

Пакеты собираются только для устройств из плана, а открыть пакет может
только адресат, так что сервер не раздаст ключ кому-то ещё.

### Подтверждение на остальных устройствах

Пакет нового ключа привязан к старому ключу группы и подписан ключом
инициатора. Исключённое устройство старый ключ знает и подписать пакет своим
ключом может. Его карточка у остальных лежит среди проверенных: до исключения
оно было обычным участником. Если сервер с ним заодно, он может прислать
любому устройству группы `Rekeyed` с таким пакетом, и раньше устройство само
перешло бы в группу исключённого и слало бы туда буфер, включая пароли.

Поэтому сам движок переходит только на ключ, который выпустило это же
устройство (пакет подписан его ключом, подделать это никто не может; так
приходит свой пакет после потерянного ответа на `Rekey`). Пакет от любого
другого устройства — вопрос человеку:

- Движок останавливается и сообщает `RekeyOffered(RekeyNotice)`: новый ключ,
  инициатор, его имя и ОС из проверенной карточки. Дальше он не подключается
  и ничего не отправляет.
- Приложение сохраняет предложение в `<state dir>/rekey-offer.bin`
  (`devices::save_offer`; файл защищён так же, как `state.bin`), запускает
  сервис без синхронизации, ставит статус `awaiting`, шлёт
  `clipwire://group-rekey-offered` и системное уведомление. Вопрос переживает
  перезапуск: пока файл есть, синхронизация не запускается ни со старым
  ключом, ни с новым.
- В «Синхронизации» вместо обычного раздела вопрос: «Устройство „MacBook“
  (macOS, отпечаток ab12…) сменило ключ группы. Новый ключ пришёл сюда
  тогда-то. Перейти на него?». Время — когда пакет пришёл на это устройство:
  времени смены в пакете нет, а серверу здесь верить нельзя.
- «Перейти на новый ключ» (`group_rekey_accept` → `devices::accept_offer`):
  `adopt_key`, файл предложения удаляется, сервис запускается с новым ключом.
  Связь с сервером для этого не нужна.
- «Это не я, не переходить» (`group_rekey_decline` → `devices::decline_offer`):
  новый ключ выбрасывается, устройство помечается исключённым. Дальше как
  после `Excluded`: «Выйти из группы» или «Попробовать снова» (тогда сервер
  пришлёт пакет ещё раз, и вопрос появится снова).

Так же обрабатывается `Rekeyed`, пришедший посреди живого соединения, когда
устройство было в сети во время смены. Отдельного правила для этого случая
нет: и при входе, и в живом соединении сообщение присылает сервер, момент
выбирает он, и о том, кто на самом деле сменил ключ, живое соединение ничего
не говорит.

Исключений «инициатор — админ группы» или «карточка инициатора давно
знакома» нет. Кто админ, известно только со слов сервера, а давно знакомая
карточка есть и у исключённого устройства. Цена: после каждой смены ключа на
каждом остальном устройстве надо один раз нажать «Перейти». Смена ключа —
редкое действие, а ошибка здесь стоит всего буфера обмена.

Чего подтверждение не закрывает. Имя в карточке устройство выбирает само,
так что исключённое может назваться именем другого ноутбука. Отличает их
отпечаток: его стоит сверить с тем, что показывает устройство, на котором
ключ меняли на самом деле. Если человек нажмёт «Перейти», не глядя, защита
не сработает.

Свойства: исключённое устройство не получает новый ключ и теряет доступ к
серверу группы (старая группа больше ничего не отдаёт), к прямой передаче
(p2p-ключ выводится из ключа группы) и к содержимому новых файлов. Ранее
полученное у него остаётся, это не отменить. Локальная история на остальных
устройствах не трогается.

Если группа держит файлы во внешнем хранилище (S3 или SFTP,
`docs/storage.md`), доступы к нему остаются у исключённого устройства и у
устройств без карточки, которые новый ключ не получат. Новые
файлы оно не прочитает (части зашифрованы новым ключом), но может удалять и
портить объекты в хранилище, а у SFTP у него остаётся вход на сервер. Молча
доступы не сбрасываются. Диалог смены ключа (и с удалением, и без, если есть
устройства без карточки) предупреждает, что ключ S3 или пароль и ключ SSH
надо сменить у поставщика и сохранить в настройках. Новые настройки уходят с
пометкой `access_exposed`, и карточка «Хранилище файлов» напоминает об этом
на всех устройствах, пока не сохранят другой секрет или другое хранилище.

Токен relay (`relay_token` из приглашения) тоже остаётся у исключённого
устройства. Группу оно не прочитает и, с сервера 0.5.0, новых групп не создаст
(для этого нужен ключ администратора), но до relay достучится. Токен общий для
всех устройств сервера, поэтому сменой ключа группы он не сбрасывается. Если
устройство могло попасть в чужие руки, администратор сервера меняет токен relay
из клиента (`RotateRelayToken`, см. `docs/architecture.md`), и все устройства
вводят новый код приглашения.

## Сервер

Код — `crates/clipwire-server/src/devices.rs` (обработка сообщений) и
`src/store/devices.rs` (база).

**База.** Таблица `cards (group_id, device_id, card, updated_ms)` — последняя
карточка устройства в группе. Таблица `rekeys (group_id, device_id, envelope)` —
пакеты нового ключа. В `groups` три столбца: `rotated_to` (id новой группы),
`rotated_ms` (когда сменили ключ) и `tombstone_ms` (когда группа стала
надгробием); у обычной группы они пустые. Карточки и пакеты удаляются каскадом
вместе с группой.

**`PublishCard`.** Карточка пишется под `DeviceId` соединения, содержимое сервер
не разбирает. Карточка больше 4096 байт — ответ `Error`, соединение не рвётся.
Ответа на успешную публикацию нет; соединение обрабатывает сообщения по порядку,
так что `ListDevices` после `PublishCard` уже видит новую карточку.

**`ListDevices` → `Devices`.** Все устройства группы из таблицы `devices`, по
возрастанию id: карточка (пустая, если не публиковалась), `last_seen_ms` —
время последнего входа в группу, `online` — есть ли у устройства открытое
соединение с этой группой.

**`Rekey { new_group, envelopes }`** в старой группе. Проверки:

- `new_group` есть на сервере, отличается от старой и сама не в режиме «ключ
  сменён»;
- отправитель уже вошёл в `new_group` (так нельзя увести участников в чужую
  группу);
- старая группа ещё не в режиме «ключ сменён»;
- пакеты только для устройств старой группы, без повторов, не больше числа её
  устройств, каждый не длиннее 512 байт.

Если всё в порядке, в одной транзакции группа помечается, пакеты сохраняются,
элементы, файлы и карточки старой группы удаляются. Файлы с диска убираются
следом в фоне, под тем же замком, что при отмене загрузки; ждущие `Get` получают
`Cancelled`.

Ответ отправителю: сервер закрывает поток без `Error` (чистый конец потока).
Отказ — `Error` с причиной, затем закрытие, как у любой ошибки. Пакет для себя
отправитель класть не обязан, но может: при повторном входе в старую группу
(например, если ответ потерялся) без пакета он получит `Excluded`, с пакетом —
свой `Rekeyed`. Агент, у которого новый ключ уже сохранён, на `Excluded` из
старой группы не реагирует.

Остальные соединения старой группы сервер будит (`Hub::kick`): каждое отправляет
своему устройству `Rekeyed { envelope }` или `Excluded` и закрывает поток.
Соединение, которое вошло в группу в момент смены ключа, после регистрации
проверяет режим группы ещё раз и закрывается так же.

**Вход в группу со сменённым ключом.** Сначала проверяется секрет: с чужим —
обычный отказ. С верным — вместо `Joined` и истории одно сообщение (`Rekeyed`
для `DeviceId` соединения или `Excluded`), затем закрытие. `Push`, `Backfill` и
файлы в такую группу не принимаются: элемент отбрасывается, загрузка файла
получает `BlobFail::Protocol("ключ группы сменён")`.

**Срок.** Группа со сменённым ключом не считается заброшенной (её не трогает
чистка групп, в которые 90 дней никто не входил). Через 30 дней после
`rotated_ms` (`Guards::rotated_keep`) обычный цикл чистки удаляет её пакеты,
карточки и устройства (`Store::purge_rotated`), а строку группы оставляет
навсегда надгробием с `tombstone_ms`. Удалять строку нельзя: вход со старым
ключом и токеном сервера создал бы группу с тем же id заново, и исключённое
устройство снова оказалось бы «в группе». Вход в надгробие с верным секретом
получает `Excluded` (пакетов больше нет), с чужим — обычный отказ. До срока
сменённая группа занимает место в пределе `CLIPWIRE_MAX_GROUPS`, надгробие —
нет: оно занимает в базе одну короткую строку.

## Клиент

Код — `crates/clipwire-agent/src/devices.rs` (карточка, разбор списка, кому
достаётся ключ, состояние на диске), движок — `src/sync.rs`, приложение —
`apps/desktop/src-tauri/src/devices.rs` и `apps/desktop/src/settings/Devices.svelte`.

**Карточка.** Движок после входа в группу (после истории) отправляет
`PublishCard` и сразу `ListDevices`. Ответ `Devices` подтверждает, что сервер
карточки знает. Если соединение рвётся в первые 10 секунд после карточки без
этого ответа, движок считает сервер старым и до перезапуска карточки не шлёт
(сервер до этой волны не разбирает `PublishCard` и закрывает соединение). Имя
в карточке обрезается до 100 символов. Смена имени в настройках перезапускает
сервис, поэтому карточка публикуется заново.

**Команды.** Интерфейс говорит с движком через `devices::Controller` (канал
`Control` в движок): `list_devices` и `rekey(remove, confirmed)`. Пока нет
связи, команды сразу получают отказ «Нет связи с сервером». Команды Tauri:
`devices_list` (в каждой записи `first_seen_ms` — когда этот клиент впервые
увидел карточку), `device_remove(device_id, confirmed, also_remove)` (id —
64 hex), `group_rekey(confirmed, remove)`. Две последние возвращают новый код
приглашения и отпечатки устройств без карточки, которым ключ не достался.
Для ответа на чужую смену ключа: `group_rekey_offer` (кто сменил ключ, или
`null`), `group_rekey_accept`, `group_rekey_decline`.

**Смена ключа на этом устройстве** идёт внутри сессии движка: `ListDevices`,
проверка карточек и `plan_rekey` (себя удалить нельзя, удаляемое должно быть в
группе, устройство с карточкой вне подтверждённого набора отменяет смену),
новый ключ, вход в новую группу вторым соединением того же эндпоинта,
карточка там и `ListDevices` как подтверждение записи, пакеты `seal_rekey` для
всех остающихся с карточкой и для себя, `Rekey` в старой группе. Успех — сервер
закрыл поток. Дальше движок не подключается и ждёт, пока его снимут, а
приложение сохраняет ключ (`adopt_key`: тот же сервер и ключ устройства, курсор
остаётся, очередь загрузок и outbox удаляются, их файлы были в старой группе) и
перезапускает сервис.

**Проверенные карточки.** Каждый ответ `Devices` движок открывает
(`open_entries`) и запоминает карточки, которые прошли проверку
(`Engine::learn`). Изменения уходят событием `KnownDevices`, сервис сохраняет
их в `<state dir>/devices.bin` вместе с id группы (`devices::save_known`), а
новый движок получает их при запуске (`with_known_devices`). Так выключенное
устройство, которому пакет приходит сразу при входе, когда список уже не
спросить, может проверить инициатора. Рядом с карточками в файле лежит время,
когда клиент увидел каждое устройство впервые (`devices::first_seen`): по нему
диалог смены ключа выделяет недавние устройства. У карточек из файла прежней
версии время 0, то есть «давно». Список обновляется при входе, раз в
5 минут и при элементе с устройства без карточки (не чаще раза в 30 секунд).
При смене ключа карточки переходят в новую группу (`adopt_key`), при выходе из
группы удаляются.

**Приём.** `Rekeyed` (при входе вместо `Joined` или посреди сессии) движок
открывает `open_rekey` и сверяет `initiator` пакета. Это устройство — событие
`Rekeyed(RekeyNotice)`: приложение делает `adopt_key` и перезапускает сервис.
Другое устройство с проверенной карточкой — событие `RekeyOffered(RekeyNotice)`
с ключом, инициатором, его именем и ОС: ключ ждёт ответа человека (см.
«Подтверждение на остальных устройствах»). После «Перейти» интерфейс получает
`clipwire://group-rekeyed { by_me, by, result }` и пишет «ключ группы сменило
устройство «имя»». Пакет, который не открылся, и незнакомый инициатор равны
`Excluded`. Ограничение: устройство, которое вошло в группу после последнего
обновления списка и сразу сменило ключ, для остальных незнакомо, и они
считают себя исключёнными.

`Excluded` → событие `Excluded { old }`. Ключ не стирается: такое сообщение
сервер может прислать и без смены ключа. Приложение пишет отметку
`<state dir>/excluded` с id группы (`devices::mark_excluded`), перезапускает
сервис без синхронизации (история и окно вставки работают), статус —
`excluded`, и шлёт `clipwire://group-excluded`. В «Синхронизации» вместо
обычного раздела сообщение и две кнопки: «Выйти из группы» (`leave_group`,
`Paths::reset` стирает ключ и отметку) и «Попробовать снова» (`group_retry`:
отметка снимается, сервис запускается с тем же ключом). Отметка переживает
перезапуск приложения. Консольный агент: `clipwire-agent run` с отметкой не
запускается, `clipwire-agent retry` её снимает. С чужой сменой ключа он
поступает так же, как приложение: запоминает предложение и останавливается,
`run` с ним не запускается, отвечают командами `clipwire-agent rekey-accept`
и `clipwire-agent rekey-decline`.

Оба шага сверяют `old` с группой на диске: если там уже другая группа,
событие игнорируется. Так `Excluded` из старой группы не тронет устройство,
которое уже на новом ключе. Если `adopt_key` записал ключ, но следом что-то
не удалось (очередь загрузок не удалилась — это только запись в лог), сервис
всё равно перезапускается, раз на диске уже новая группа.

**Потерянный ответ на `Rekey`.** Если соединение оборвалось после отправки
`Rekey`, команда получает «Ответ сервера не пришёл, проверяю…», а движок
помнит новый ключ и план. Пришёл при повторном входе свой `Rekeyed` с этим
ключом — `RekeyNotice { by_me: true, skipped }`, и интерфейс получает тот же
успех, что при обычной смене: новый код приглашения и пропущенные устройства.
Вход прошёл как обычно — сервер запрос не получил, событие `RekeyLost` и
`clipwire://group-rekey-failed` с текстом «Ключ не сменился…».

**Интерфейс.** В «Синхронизации» блок «Устройства группы»: имя (или
«Неизвестное устройство»), ОС, отпечаток, в сети ли и когда было последний
раз, у всех кроме своего — «Удалить». Кнопка «Сменить ключ группы». Перед
подтверждением список перечитывается и показывается, что будет с удаляемым и
с остальными, какие неизвестные устройства ключ не получат и что код
приглашения сменится. Ниже — получатели нового ключа с галочками, отпечатком
и временем появления; недавние выделены. Логика подписей и набора id для
команды — в `apps/desktop/src/lib/devices.ts` (`recipients`, `rekeyChoice`,
`isFresh`, `offerText`).

## Приложение-источник

- При копировании на Windows — владелец буфера уже известен (exe). Имя для
  показа: `FileDescription` из ресурсов версии exe, если нет — имя файла без
  `.exe`. Иконка: 32×32 из exe (`SHGetFileInfo` или `ExtractIconEx`) → PNG,
  кэш по пути exe в памяти. Не получилось — без иконки.
- `SourceApp` кладётся в `Item.ext` (`ext::SOURCE_APP`) и в запись истории
  (`Entry` тоже получает `ext`, чтение старых записей — как в `history.rs`).
- В окне вставки: маленькая иконка и имя приложения в строке меты, поиск по
  имени приложения.
- Если источника нет (буфер без владельца) — ничего не показывать.

Как сделано:

- `crates/clipwire-agent/src/source_app.rs`: `lookup(путь exe)` — имя из
  `FileDescription` (языки из `\VarFileInfo\Translation`, запасные 0409/04b0,
  0409/04e4), иконка `PrivateExtractIconsW` 32×32 → `GetIconInfo` /
  `GetDIBits` → PNG; у иконок без альфа-канала прозрачность из маски. Кэш по
  пути exe без учёта регистра, на время работы. На других ОС — имя файла без
  иконки.
- `clipboard.rs` отдаёт полный путь exe владельца; список исключений
  сравнивается по имени файла, как раньше.
- `Entry.ext` в истории, старые записи без `ext` читаются как `EntryV3`.
  Повтор того же содержимого с новым источником заменяет метку, без
  источника — оставляет прежнюю. Поиск (`History::list`) — по имени
  приложения, иконка для этого не разбирается.
- Входящий элемент: `Entry.ext = Item.ext`.
- Свой элемент: канал копирований в движок несёт `sync::Outgoing { content,
  ext }`. `Copier` кладёт туда `SourceApp` из буфера ОС, `Service::copy` (вставка
  из истории) — источник записи, редактор картинок — ничего. `Engine::push`
  и отправка локальной истории (`backfill`, `ext` из записи) кладут `ext` в
  `Item.ext`, так что другие устройства видят приложение-источник.
- `EntryDto.source_app`: `{ name, icon }` (icon — data URL PNG или `null`)
  или `null`. В окне вставки — `lib/AppTag.svelte` (иконка 14 px и имя) в
  строке меты и в мете предпросмотра.
