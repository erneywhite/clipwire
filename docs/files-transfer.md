# Передача файлов через сервер

Части 2 и 3 этапа файлов: файлы до порога уходят на сервер зашифрованными и
скачиваются на другом устройстве при вставке. Часть 4 (файлы крупнее порога
напрямую через iroh) здесь не описана.

Уже готово и не меняется без согласования:

- `crates/clipwire-core/src/blob.rs`: части по 1 МиБ (`CHUNK`), `BlobId`,
  `GroupKey::blob_key(id)`, `BlobKey::seal/open(index, last, …)`, `chunk_count`,
  `chunk_len`, `sealed_size`, `OVERHEAD` (40 байт на часть).
- `crates/clipwire-core/src/proto.rs`: ALPN `clipwire/3`, `BlobRequest`,
  `BlobChunk`, `BlobReply`, `BlobFail`.
- `FileRef { name, path, size, is_dir, width, height, modified_ms, blob }`.

## Поток файла

После `Join` по основному потоку агент может открывать на том же соединении
дополнительные двунаправленные потоки (`open_bi`). Каждый поток — один файл.
Кадры те же, что в основном потоке: 4 байта длины + postcard.

**Загрузка (агент → сервер):**

1. Агент: `BlobRequest::Put { blob, size }` (`size` — открытый текст).
2. Сервер проверяет лимиты и отвечает `BlobReply::PutReady { have }` или
   `BlobReply::Error(..)` и закрывает поток.
3. Агент шлёт `BlobChunk { index, data }` строго по порядку с `index = have`,
   до `chunk_count(size) - 1`. `data` — результат `BlobKey::seal(index, last, …)`,
   длина ровно `chunk_len(size, index) + OVERHEAD`.
4. Агент закрывает свою сторону потока (`finish`), сервер отвечает `Stored`.

Если файл уже загружен целиком, `have == chunk_count(size)`: агент сразу
закрывает поток и получает `Stored`. Докачка после обрыва — тем же `Put`:
сервер вернёт, сколько частей у него есть.

**Скачивание (сервер → агент):**

1. Агент: `BlobRequest::Get { blob, from }`.
2. Сервер: `GetReady { size, have, complete }` или `Error(NotFound)`.
3. Сервер шлёт `BlobReply::Chunk(BlobChunk)` с `index` от `from` по порядку.
   Если файл ещё загружается, ждёт новых частей. Нет новых частей дольше
   `blob_stall` (по умолчанию 120 с) — `Error(Stalled)`.
4. После последней части сервер закрывает поток.

Агент проверяет каждую часть: `BlobKey::open(index, index == count - 1, data)`.
Ошибка расшифровки — файл испорчен или подменён, скачивание прерывается, часть
не пишется.

## Сервер

- Настройки из окружения: `CLIPWIRE_MAX_FILE_BYTES` (по умолчанию 104857600,
  100 МиБ, открытый текст), `CLIPWIRE_BLOB_QUOTA` (по умолчанию 2147483648 на
  группу, считается по `sealed_size`), `CLIPWIRE_BLOB_STALL_SECS` (120). Срок
  жизни — тот же `CLIPWIRE_TTL_HOURS`, от момента создания файла.
- Хранение: `<data_dir>/blobs/<group_id hex>/<blob_id hex>` — части подряд,
  часть `i` лежит со смещения `i * (CHUNK + OVERHEAD)`. Имена только из
  разобранных id, никаких строк от клиента в путях.
- Метаданные в SQLite: таблица `blobs (group_id, blob_id, size, have,
  created_ms, PRIMARY KEY (group_id, blob_id))`.
- `Put`: `size > max_file` → `TooLarge { max }`; новый файл не влезает в квоту
  (сумма `sealed_size` файлов группы) → `QuotaExceeded`; файл есть с другим
  размером → `SizeMismatch`. Часть с неожиданным `index` или длиной →
  `Protocol(..)`. После каждой части обновляется `have`.
- Ожидающие `Get` узнают о новых частях без опроса диска (например,
  `tokio::sync::watch` на файл в памяти сервера).
- Чистка по сроку вместе с элементами: удалить строки и файлы.
- Не больше 8 потоков файлов одновременно на соединение, лишние ждут.

## Клиент (агент и Rust-часть приложения)

**Отправка.** Когда в группе (не локальный режим) копируются файлы, сервис
назначает `blob = Some(BlobId::random())` каждому файлу (не папке) размером не
больше настройки `file_upload_limit_mb` (по умолчанию 100; 0 — файлы не
загружать). Элемент `Content::Files` сразу уходит в группу (карточка появляется
везде), запись в истории — с этими же `blob`. Загрузки ставятся в очередь.

- Очередь сохраняется в `<state dir>/uploads.json`
  (`[{ blob, path, size, modified_ms }]`) и переживает перезапуск.
- Загрузчик живёт в движке (у него соединение), до 2 файлов одновременно. Перед
  загрузкой и в процессе сверяет размер и `modified_ms` файла: изменился —
  загрузка отменяется с ошибкой «файл изменился после копирования».
- Обрыв связи — файл остаётся в очереди, после переподключения докачка (`Put`
  вернёт `have`).

**Скачивание.** Для записи с другого устройства файлы скачиваются в кэш:
`<state dir>/files/<blob hex>/<имя>`. Сначала в `<имя>.part`, после проверки
последней части — переименование. Докачка: `from = длина .part / CHUNK`
(хвост, не кратный CHUNK, отрезается). Уже скачанный файл повторно не качается.
Элемент с файлами уходит в группу раньше, чем источник начнёт загрузку, поэтому
на `Error(NotFound)` агент повторяет `Get` раз в 0,5 с до 10 с и только потом
сообщает, что файла нет на сервере.

Имя файла от другого устройства перед записью на диск очищается: только
последний компонент пути, без `\ / : * ? " < > |` и управляющих символов, без
точек и пробелов в конце, зарезервированные имена Windows (`CON`, `PRN`, `AUX`,
`NUL`, `COM1`…`COM9`, `LPT1`…`LPT9`, с расширением тоже) получают префикс `_`,
пустое имя — `file`. Обязательно покрыть тестами.

**События** для интерфейса — Tauri-событие `clipwire://transfer`, не чаще раза в
200 мс на файл плюс финальное:

```json
{ "blob": "<32 hex>", "direction": "up" | "down",
  "done": 123, "total": 456,
  "state": "active" | "done" | "failed", "error": "текст" | null }
```

**Команды Tauri:**

- `popup_paste` для записи с файлами: локальная запись с файлами на месте —
  как раньше (пути). Иначе файлы с `blob` скачиваются (команда ждёт окончания,
  прогресс идёт событиями), в буфер кладутся пути из кэша. Файлы без `blob`
  (папки, большие файлы) — ошибка с их именами: «есть только на устройстве
  «X»: …». Если часть файлов скачалась, а часть нет — ошибка, ничего не кладём.
- `files_download(id: String) -> Result<(), String>` — скачать без вставки.
- `transfers() -> Vec<TransferDto>` — текущие передачи (тот же JSON, что в
  событии) для начального состояния окна.

**`FileDto`** (в `EntryDto.files`) получает поля:

```json
{ "name", "path", "size", "is_dir", "exists",
  "blob": "<32 hex>" | null,
  "local_path": "путь на этом компьютере" | null,
  "remote": true | false }
```

`local_path` — исходный путь, если запись локальная и файл на месте, или путь в
кэше, если файл скачан. `exists` = `local_path` существует. `remote` — запись с
другого устройства. `file_preview` принимает и пути из кэша.

## Интерфейс (Svelte)

- Типы в `src/lib/api.ts` по JSON выше, команды `filesDownload(id)`,
  `transfers()`.
- Окно вставки слушает `clipwire://transfer`, держит карту `blob → передача`.
- Строка записи с файлами: тонкая полоса прогресса под мета-строкой, в мете
  «↑ 45%» при отправке, «↓ 12%» при скачивании, «не отправлено: причина» при
  ошибке. Для нескольких файлов прогресс суммарный.
- Предпросмотр записи с другого устройства: скачанный файл — как локальный
  (`FilePreview` по `local_path`); не скачанный — карточка «Файл на устройстве
  «X» · размер» и кнопка «Скачать» с прогрессом. Вставка скачивает сама.
  Папки и файлы без `blob` — пометка «есть только на устройстве «X»».
- Настройки, раздел про файлы: «Загружать на сервер файлы до N МБ» (поле
  числа, 0 — не загружать), поле `file_upload_limit_mb` в `Settings`.
