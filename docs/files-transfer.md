# Передача файлов через сервер

Части 2 и 3 этапа файлов: файлы до порога уходят на сервер зашифрованными и
скачиваются на другом устройстве при вставке. Часть 4 (папки и файлы крупнее
порога напрямую через iroh) — в конце документа.

Уже готово и не меняется без согласования:

- `crates/clipwire-core/src/blob.rs`: части по 1 МиБ (`CHUNK`), `BlobId`,
  `GroupKey::blob_key(id)`, `BlobKey::seal/open(index, last, …)`, `chunk_count`,
  `chunk_len`, `sealed_size`, `OVERHEAD` (40 байт на часть).
- `crates/clipwire-core/src/proto.rs`: ALPN `clipwire/3`, `BlobRequest`,
  `BlobChunk`, `BlobReply`, `BlobFail`.
- `FileRef { name, path, size, is_dir, width, height, modified_ms, blob }`.

## Поток файла

После `Join` по основному потоку агент может открывать на том же соединении
дополнительные двунаправленные потоки (`open_bi`). Каждый поток — один файл.
Кадры те же, что в основном потоке: 4 байта длины + postcard.

**Загрузка (агент → сервер):**

1. Агент: `BlobRequest::Put { blob, size }` (`size` — открытый текст).
2. Сервер проверяет лимиты и отвечает `BlobReply::PutReady { have }` или
   `BlobReply::Error(..)` и закрывает поток.
3. Агент шлёт `BlobChunk { index, data }` строго по порядку с `index = have`,
   до `chunk_count(size) - 1`. `data` — результат `BlobKey::seal(index, last, …)`,
   длина ровно `chunk_len(size, index) + OVERHEAD`.
4. Агент закрывает свою сторону потока (`finish`), сервер отвечает `Stored`.

Если файл уже загружен целиком, `have == chunk_count(size)`: агент сразу
закрывает поток и получает `Stored`. Докачка после обрыва — тем же `Put`:
сервер вернёт, сколько частей у него есть.

**Резервирование и отмена (агент → сервер, один кадр туда и обратно):**

- `BlobRequest::Reserve { blob, size }` → `BlobReply::Reserved` или
  `Error(..)`. Заводит файл с `have = 0` с теми же проверками, что `Put`
  (предел размера, квоты, другой размер того же id). Место сразу учитывается в
  квотах. Повторный `Reserve` или `Put` того же файла — как докачка.
- `BlobRequest::Abort { blob }` → `BlobReply::Aborted` (и если файла нет).
  Сервер удаляет строку и части, ждущие `Get` сразу получают
  `Error(Cancelled)`, место возвращается в квоты.

**Скачивание (сервер → агент):**

1. Агент: `BlobRequest::Get { blob, from }`.
2. Сервер: `GetReady { size, have, complete }` или `Error(NotFound)`, если
   файл неизвестен (не заводился, отменён, удалён по сроку). Заведённый через
   `Reserve` файл известен и с `have = 0`.
3. Сервер шлёт `BlobReply::Chunk(BlobChunk)` с `index` от `from` по порядку.
   Если файл ещё загружается (или только зарезервирован), ждёт новых частей.
   Нет новых частей дольше `blob_stall` (по умолчанию 120 с) — `Error(Stalled)`.
   Источник отменил файл — `Error(Cancelled)`.
4. После последней части сервер закрывает поток.

Длина кадров в потоках файлов ограничена сильнее, чем `MAX_FRAME`: первый
кадр (запрос) — до 256 байт, кадр части — до `CHUNK + OVERHEAD + 64`. Кадр
длиннее отклоняется по префиксу длины, память под него не выделяется.
Первый кадр сервер ждёт 10 с, потом отвечает `Error(Stalled)`.

Агент проверяет каждую часть: `BlobKey::open(index, index == count - 1, data)`.
Ошибка расшифровки — файл испорчен или подменён, скачивание прерывается, часть
не пишется.

## Сервер

- Настройки из окружения: `CLIPWIRE_MAX_FILE_BYTES` (по умолчанию 104857600,
  100 МиБ, открытый текст), `CLIPWIRE_BLOB_QUOTA` (по умолчанию 2147483648 на
  группу, считается по `sealed_size`), `CLIPWIRE_BLOB_TOTAL_QUOTA` (по
  умолчанию 21474836480, 20 ГиБ на весь сервер, тоже по `sealed_size`),
  `CLIPWIRE_BLOB_STALL_SECS` (120). Срок жизни — тот же `CLIPWIRE_TTL_HOURS`,
  от момента создания файла.
- Хранение: `<data_dir>/blobs/<group_id hex>/<blob_id hex>` — части подряд,
  часть `i` лежит со смещения `i * (CHUNK + OVERHEAD)`. Имена только из
  разобранных id, никаких строк от клиента в путях.
- Метаданные в SQLite: таблица `blobs (group_id, blob_id, size, have,
  created_ms, PRIMARY KEY (group_id, blob_id))`.
- `Put` и `Reserve`: `size > max_file` → `TooLarge { max }`; новый файл не
  влезает в квоту группы (сумма `sealed_size` её файлов) или в общий предел
  сервера (сумма по всем группам) → `QuotaExceeded`; обе суммы считаются в той
  же транзакции, что и вставка строки. Файл есть с другим размером →
  `SizeMismatch`. Часть с неожиданным `index` или длиной → `Protocol(..)`.
  После каждой части обновляется `have`.
- Ожидающие `Get` узнают о новых частях и об отмене без опроса диска:
  `tokio::sync::watch` на файл в памяти сервера.
- `Abort` удаляет строку и файл под замком записи файла. Чистка по сроку
  удаляет строки вместе с элементами, а файлы — под тем же замком и только если
  строки по-прежнему нет (её мог завести заново `Put` того же id).
- Пределы потоков файлов. На соединение: до 32 потоков ждут первого кадра
  (`Reserve` и `Abort` обслуживаются в этом же месте до конца, они короткие),
  пока все заняты, следующий поток сервер не принимает. `Put` и `Get` после
  первого кадра отдают это место и берут свои пропуска: до 8 на соединение,
  до 16 `Put` и отдельно до 16 `Get` на группу, до 64 `Put` и отдельно до 64
  `Get` на весь сервер; лишние ждут. Пулы `Put` и `Get` раздельные, потому что
  `Get` ждёт частей от `Put`: общий пул, занятый ждущими `Get`, остановил бы
  загрузку, которой они ждут. Сколько `Put` и `Get` может ждать пропуска на
  одном соединении, ограничивает предел потоков QUIC.

## Клиент (агент и Rust-часть приложения)

**Отправка.** Когда в группе (не локальный режим) копируются файлы, сервис
назначает новый `blob = Some(BlobId::random())` каждому файлу (не папке)
размером не больше настройки `file_upload_limit_mb` (по умолчанию 100; 0 —
файлы не загружать). Прежний `blob` тех же файлов не переиспользуется: файл
мог измениться без смены размера и времени, и докачка склеила бы старые части
с новыми. Запись в истории — с этими `blob`.

Когда движок на самом деле отправляет элемент (`Engine::push`), он сначала
резервирует все его файлы (`Reserve`, параллельно, тайм-аут 10 с на файл).
При окончательном отказе сервера (`TooLarge`, `QuotaExceeded`, `SizeMismatch`,
ошибка протокола) файлу `blob` в отправляемом элементе снимается (у получателя
это «есть только на устройстве»), в событиях передачи — `failed` с причиной.
Потом элемент уходит в группу, и только тогда загрузки ставятся в очередь.

Если резерв не дошёл (обрыв, тайм-аут, временная ошибка сервера) или
сорвалась запись `Push` в основной поток, элемент возвращается в очередь
движка вместе с уже назначенными `blob`, сессия переподключается, и элемент
уходит первым после входа. Повторный `Reserve` того же `blob` у сервера — как
докачка. На третьей попытке подряд (`MAX_RESERVE_ATTEMPTS`) файлы, резерв
которых снова не дошёл, отправляются как «есть только на устройстве», чтобы один элемент не держал синхронизацию в
цикле переподключений. Копирование, которое пока не было связи вытеснило более
новое, не грузится; если его отправка уже начиналась, его резервы отменяются
(`Abort`) при следующем соединении.

- Очередь сохраняется в `<state dir>/uploads.json`
  (`[{ blob, path, size, modified_ms, group, queued_ms }]`, `group` — `group_id`
  в hex) и переживает перезапуск. При загрузке выбрасываются задания другой
  группы и старше 24 ч. Резервы выброшенных по возрасту заданий своей группы
  отменяются (`Abort`) при первом соединении, без гарантий: не дошло —
  повтор на следующем соединении. Задания другой группы отменить нечем, их
  убирает срок хранения на сервере. Выход из группы (`Paths::reset`) удаляет файл.
- Загрузчик живёт в движке, в той же задаче (у него соединение), до 2 файлов
  одновременно. Перед загрузкой, после чтения каждой части и перед `finish`
  сверяет размер и `modified_ms` файла: изменился или пропал — загрузка
  отменяется с ошибкой «файл изменился после копирования» («файла уже нет на
  месте»). При любой неповторяемой ошибке загрузки (и при окончательном отказе
  сервера) серверу уходит `Abort`, чтобы резерв не занимал квоту до срока.
- Обрыв связи — файл остаётся в очереди, после переподключения докачка (`Put`
  вернёт `have`).
- `Service::shutdown` сначала снимает слежение за буфером (его обработчик
  держит копию отправителя в канал движка), потом закрывает канал. Движок
  дошлёт очередь и закроет соединение сам; не успел за 3 с — его задача
  снимается (`abort`) вместе с загрузчиком, чтобы новый сервис не работал с
  той же очередью.

**Скачивание.** Для записи с другого устройства файлы скачиваются в кэш:
`<state dir>/files/<blob hex>/<имя>`. Сначала в `<имя>.part`, после проверки
последней части — переименование. Каждая часть сбрасывается на диск
(`sync_data`), потом её номер пишется в `<имя>.part.ok`. Докачка:
`from = min(число из .part.ok, длина .part / CHUNK)`, всё дальше отрезается;
так после сбоя ОС не берутся части, которые не успели лечь на диск. Нет
`.part.ok` — с начала. На Windows `.part` открывается без совместного доступа.
Одновременные скачивания одного файла в процессе идут по очереди через общий
замок. Уже скачанный файл повторно не качается. Повтора на `Error(NotFound)`
нет: источник резервирует файлы до отправки элемента, а сервер сам ждёт частей.

Имя файла от другого устройства перед записью на диск очищается: только
последний компонент пути, без `\ / : * ? " < > |` и управляющих символов, без
точек и пробелов в конце, зарезервированные имена Windows (`CON`, `PRN`, `AUX`,
`NUL`, `CONIN$`, `CONOUT$`, `COM1`…`COM9`, `LPT1`…`LPT9`, `COM¹`…`COM³`,
`LPT¹`…`LPT³`, в любом регистре и с расширением тоже) получают префикс `_`,
пустое имя — `file`. Обязательно покрыть тестами.

**События** для интерфейса — Tauri-событие `clipwire://transfer`, не чаще раза в
200 мс на файл плюс финальное:

```json
{ "blob": "<32 hex>", "direction": "up" | "down",
  "done": 123, "total": 456,
  "state": "active" | "done" | "failed", "error": "текст" | null }
```

**Команды Tauri:**

- `popup_paste` для записи с файлами: локальная запись со всеми файлами на
  месте — как раньше (пути). Иначе файлы, которых нет на этом компьютере, но
  у которых есть `blob`, скачиваются в кэш (команда ждёт окончания, прогресс
  идёт событиями), в буфер кладутся пути здесь: исходные для файлов на месте,
  из кэша для остальных. Так же и для своей записи, у которой файл
  переместили или удалили. Файлы без `blob` (папки, большие файлы) — ошибка с
  их именами: у чужой записи «Есть только на устройстве «X»: …», у своей
  «Файла нет на месте, его переместили или удалили: …». Если часть файлов
  скачалась, а часть нет — ошибка, ничего не кладём.
- Если хоть один путь в буфере не исходный (чужая запись или свой файл взят
  из кэша, потому что с места пропал), пути кладутся в буфер тихо, без
  копирования: запись с подменёнными путями не уходит в историю и группу и не
  ставит загрузку заново, а сама запись поднимается наверх истории. Своя
  запись со всеми файлами на месте копируется как обычно.
- После скачивания `popup_paste` кладёт пути в буфер и жмёт Ctrl+V, только
  если окно вставки всё ещё видно и в фокусе. Закрыли окно или ушли в другую
  программу — команда возвращает `Ok` без вставки, файлы остаются в кэше.
  Окно вставки со своей стороны считает показы (`popup://opened`): если за
  время скачивания окно открыли заново или спрятали, вставку не продолжает.
- `files_download(id: String) -> Result<(), String>` — скачать без вставки
  то, чего нет на этом компьютере (и для своей записи с пропавшим файлом).
- `transfers() -> Vec<TransferDto>` — текущие передачи (тот же JSON, что в
  событии) для начального состояния окна.

**`FileDto`** (в `EntryDto.files`) получает поля:

```json
{ "name", "path", "size", "is_dir", "exists",
  "blob": "<32 hex>" | null,
  "local_path": "путь на этом компьютере" | null,
  "remote": true | false }
```

`local_path` — исходный путь, если запись локальная и файл на месте, или путь в
кэше, если файл скачан (у своей записи кэш — запасной вариант, когда исходный
файл пропал). `exists` = `local_path` существует. `remote` — запись с другого
устройства. `file_preview` принимает и пути из кэша.

`file_preview` отдаёт `pdf`, `video` или `audio` только если начало файла
совпадает с сигнатурой типа (`%PDF-`, `ftyp`/`moov`…, WebM, Ogg, ID3, кадр
MP3/AAC, `fLaC`, RIFF/WAVE). asset-протокол определяет тип по содержимому, и
HTML с расширением `.pdf` иначе открылся бы в iframe как страница. Не совпало —
файл показывается как обычный (текстом, если это текст). Разрешение для
asset-протокола не отзывается до перезапуска: в tauri 2 нет удаления из scope.

## Интерфейс (Svelte)

- Типы в `src/lib/api.ts` по JSON выше, команды `filesDownload(id)`,
  `transfers()`.
- Окно вставки слушает `clipwire://transfer`, держит карту `blob → передача`.
- Строка записи с файлами: тонкая полоса прогресса под мета-строкой, в мете
  «↑ 45%» при отправке, «↓ 12%» при скачивании, «не отправлено: причина» при
  ошибке. Для нескольких файлов прогресс суммарный.
- Предпросмотр записи с другого устройства: скачанный файл — как локальный
  (`FilePreview` по `local_path`); не скачанный — карточка «Файл на устройстве
  «X» · размер» и кнопка «Скачать» с прогрессом. Вставка скачивает сама.
  Папки и файлы без `blob` — пометка «есть только на устройстве «X»».
  Своя запись с пропавшим файлом, у которого есть `blob`, — та же карточка
  «Файла нет на месте, копия есть на сервере» с кнопкой «Скачать».
- Ошибку скачивания или вставки обновление списка не стирает. Её сбрасывают
  явные действия: новый запрос, смена вкладки, новое открытие окна, новая
  вставка.
- Настройки, раздел про файлы: «Загружать на сервер файлы до N МБ» (поле
  числа, 0 — не загружать), поле `file_upload_limit_mb` в `Settings`.

# Часть 4: папки и файлы больше порога

Основа уже есть и без согласования не меняется: `FileRef.blob_size` и
`FileRef.p2p` (`crates/clipwire-core/src/item.rs`), чтение записей прошлого
формата (`item::legacy`, `History::decrypt`), проверка участника и ALPN
`clipwire-p2p/1` (`crates/clipwire-core/src/p2p.rs`).

## Что как передаётся

При копировании в группе сервис решает для каждого элемента `Content::Files`:

| Что | Условие | `blob` | `blob_size` | `p2p` |
|---|---|---|---|---|
| файл | `size ≤ порог` | новый | `size` | `false` (через сервер, как сейчас) |
| файл | `size > порог` | новый | `size` | `true` (напрямую) |
| папка | суммарный размер `≤ порог` | новый | размер архива | `false` |
| папка | больше порога | новый | размер архива | `true` |
| что угодно | порог 0, локальный режим | `None` | 0 | `false` |

Порог — та же настройка `file_upload_limit_mb`. При `0` ничего не передаётся
вообще (ни через сервер, ни напрямую). Прямая передача включена всегда, когда
порог не 0: отдельной настройки нет.

## Папки

- Папка передаётся одним архивом **tar без сжатия** (крейт `tar`, уже в
  lock-файле). Архив собирается во временный файл
  `<state dir>/outbox/<blob hex>.tar`; дальше всё как с обычным файлом:
  шифрование частями, докачка, кэш. `blob_size` — размер архива; чтобы его
  знать до отправки элемента, архив собирается до `Engine::push` (для папки
  до порога — сразу при копировании в фоне сервиса; элемент уходит в группу,
  когда архив готов). Для папки больше порога архив собирается лениво, при
  первом запросе получателя, и тоже кладётся в outbox.
- Обход папки с пределами: не больше 100 000 записей и не глубже 64 уровней;
  ссылки (symlink, junction) не разыменовываются и в архив не попадают.
  Превысили предел — папка не передаётся (`blob = None`), в событиях `failed`
  с причиной (у события свой случайный `blob`, к записи он не привязан).
- Размер `FileRef.size` у папки — сумма размеров файлов внутри (для показа).
- Обход и сборка архива идут не в потоке буфера ОС, а в фоновой задаче
  сервиса (`spawn_blocking`). Запись с папкой попадает в историю и в группу,
  когда решение принято (для папки до порога — когда готов архив).
- В архиве пути от корня папки через `/`, без самой папки; только записи
  «папка» и «файл» (заголовки GNU, длинные имена — расширением GNU). Размер
  архива зависит только от путей и размеров, поэтому для папки больше порога
  `blob_size` считается без чтения файлов (`folder::tar_size`), а архив,
  собранный позже, обязан совпасть с ним по размеру. При ленивой сборке
  источник обходит папку заново: другой суммарный размер или размер архива —
  `BlobFail::Cancelled` («папка изменилась после копирования»).
- Распаковка: каждая запись проверяется отдельно, принимаются только
  обычные компоненты пути (абсолютные пути, диски Windows, UNC и `..` —
  ошибка), каждый компонент очищается как имя файла; ссылки, жёсткие ссылки
  и устройства — ошибка. Распаковка идёт во временную `<имя>.unpack` и
  переименовывается в `<имя>`, так что недораспакованная папка не выглядит
  скачанной. При ошибке временная папка удаляется.
- Архив папки до порога загружается как обычный файл: задание очереди с
  `outbox: true` указывает на архив. После загрузки или окончательного отказа
  архив удаляется. Выход из группы (`Paths::reset`) удаляет весь outbox.
- Получатель скачивает архив в `<files>/<blob hex>/<имя>.tar` и распаковывает
  в `<files>/<blob hex>/<имя>/` (очищенное имя, как у файлов), затем удаляет
  архив. Распаковка только безопасная: `tar::Archive::unpack` в отдельную
  папку, абсолютные пути и `..` отвергаются (проверить тестом с вредным
  архивом). В буфер кладётся путь папки.
- outbox чистится: архив удаляется после успешной загрузки на сервер; архивы
  для прямой передачи — через 24 часа после создания (при старте сервиса).

## Прямая передача (`clipwire-p2p/1`)

- Эндпоинт агента (тот же, что для сервера) принимает входящие соединения с
  ALPN `clipwire-p2p/1`. Проверка участника — по `p2p.rs`: Hello → Challenge →
  Proof → Accepted/Denied на первом потоке; `requester`/`source` — id
  эндпоинтов (`conn.remote_id()` и свой). Тайм-аут проверки 10 с, неверное
  доказательство — `Denied` и закрытие.
- После `Accepted` получатель открывает потоки `BlobRequest::Get { blob, from }`;
  источник отвечает `GetReady { size: blob_size, have: count, complete: true }`
  и шлёт `Chunk` по порядку, читая части с диска (файл — исходный путь из
  своей истории, папка — архив из outbox) и шифруя `GroupKey::blob_key`.
  Источник обслуживает только blob из своих локальных записей истории с
  `p2p = true`; перед отдачей сверяет размер и `modified_ms` файла (изменился —
  `BlobFail::Cancelled`), неизвестный blob — `NotFound`. Не больше 4 потоков
  на соединение и 8 входящих соединений одновременно.
- Получатель подключается к `EndpointAddr(origin)` с relay-адресом своего
  сервера (у всех устройств группы один relay). Тайм-аут подключения 15 с; не
  вышло — ошибка «устройство «X» не в сети». Части пишутся тем же
  `PartWriter` (докачка, `.part.ok`), в тот же кэш, события `direction: down`.
- Ошибки прямой передачи лежат в `anyhow::Error` как
  `clipwire_agent::p2p::P2pError` (`Offline`, `Denied`, `BadProof`,
  `OwnDevice`); имени устройства в них нет, его подставляет приложение.
  `NotFound` и `Cancelled` от источника переводятся в текст «на
  устройстве-источнике этого файла уже нет в истории» и «файл на
  устройстве-источнике изменился или пропал после копирования».
- Проверенное соединение с источником переиспользуется для следующих файлов,
  пока оно живо. Источник отдаёт только `Get`, на остальное — `Protocol`;
  первый кадр потока — до 256 байт, ждёт его 10 с.
- Свои файлы источник ищет в своей истории (`History::local_p2p_file`):
  сервис передаёт этот поиск в `Blobs::set_p2p_sources`.
- `Blobs::download` по `p2p` выбирает путь: через сервер или напрямую. Для
  прямого нужен `origin` записи — сигнатуры `download`/`download_all`
  получают его (поменять вызовы в `apps/desktop`).
- Загрузчик на сервер файлы с `p2p = true` не трогает, резервирование тоже.

## Интерфейс

- Строка и предпросмотр: файл/папка с `p2p` и не скачанные — «напрямую с
  устройства «X» · размер», кнопка «Скачать»; ошибка подключения —
  «устройство «X» не в сети». Папка — иконка папки, размер содержимого,
  после скачивания «Показать в папке» открывает распакованную папку.
- Вставка, выбранные файлы, прогресс — как для обычных файлов.
- `FileDto` получает `p2p` и `blob_size`. Скачиваемым считается любой файл
  или папка с `blob`, кроме своего p2p-файла, пропавшего с места: брать его
  не у кого. «Есть только на устройстве «X»» — только при `blob = null`.
- Ошибку `P2pError::Offline` приложение дополняет именем устройства из
  записи: ««имя» не скачался: устройство «X» не в сети».
- Папку «Показать в папке» открывает командой `folder_open(path)`: путь
  проверяется по истории, открывается только каталог.
